# ТЗ на плавный переход с Chainlit на Open WebUI с полноценной RAG-архитектурой

См. также:
- [MIGRATION_OVERIEW_WITH_LEAKS.md](./MIGRATION_OVERIEW_WITH_LEAKS.md)
- [MIGRATION_TOOLS.md](./MIGRATION_TOOLS.md)

## 1. Цель проекта

- [ ] **Перевести текущую систему с Chainlit на Open WebUI без потери существующей бизнес-логики.**
  
  **Контекст:** текущая реализация уже содержит рабочие элементы: роутинг запросов, document-question flow, session-документы, knowledge-base слой, hybrid retrieval, confidence/fallback-эвристики. Задача не в полном переписывании с нуля, а в переносе на более устойчивую продуктовую архитектуру.

- [ ] **Убрать критическую зависимость от session-only индекса и самописного локального хранения retrieval-состояния.**
  
  **Контекст:** текущая логика удобна для прототипа, но плохо масштабируется, плохо переживает рестарты, несколько воркеров и долгую эксплуатацию.

- [ ] **Перейти к разделению на продуктовые слои: UI, orchestration, ingestion, vector storage, metadata storage, reranking.**
  
  **Контекст:** Open WebUI должен стать интерфейсом и точкой входа, а не местом, где живёт весь retrieval/runtime.

- [ ] **Сохранить текущий сценарий плавного перехода без большого “big bang rewrite”.**
  
  **Контекст:** существующий Chainlit-контур должен поэтапно замещаться модулями новой архитектуры, чтобы на каждом этапе система оставалась работоспособной.

---

## 2. Исходные вводные и ограничения

- [ ] **Зафиксировать, что текущая система представляет собой прототипную гибридную RAG-архитектуру с кастомным orchestration-слоем.**
  
  **Контекст:** уже реализованы chunking, retrieval, knowledge base ingestion/retrieval, classifier, runtime orchestration, pipeline, session overlay. Это ценный задел, который нужно переиспользовать концептуально, а не выбрасывать.

- [ ] **Зафиксировать, что целевая система должна быть self-hosted friendly.**
  
  **Контекст:** приоритет на локальный или контролируемый deployment без обязательной привязки к managed SaaS.

- [ ] **Зафиксировать, что основной UX должен перейти в Open WebUI.**
  
  **Контекст:** пользовательский вход, чат, выбор модели, knowledge-интеграция, tools/functions, pipes — через Open WebUI.

- [ ] **Зафиксировать, что существующий роутинг должен быть сохранён как отдельный слой логики.**
  
  **Контекст:** маршрутизация общего чата, вопросов по документу, сравнений, summary и специальных режимов не должна потеряться при переносе в новый UI.

- [ ] **Зафиксировать, что проект должен поддерживать работу и с “долговременной knowledge base”, и с “только что загруженными в чат документами”.**
  
  **Контекст:** это два разных источника знаний, которые должны объединяться предсказуемо.

## 3. Целевая архитектура

### 3.1 Архитектурный принцип

- [ ] **Принять целевую архитектуру как набор независимых сервисных слоёв.**
  
  **Контекст:** итоговая система должна состоять не из одного монолитного RAG-модуля, а из нескольких слоёв:
  - Open WebUI — UI и точка входа;
  - Orchestration API / Pipeline service — маршрутизация и бизнес-логика;
  - Ingestion worker — обработка документов;
  - Vector DB — хранение dense/sparse retrieval индексов;
  - Metadata DB — пользователи, чаты, документы, версии, связи;
  - Reranker service — пересортировка кандидатов;
  - Optional cache/queue — Redis или аналог для фоновых задач и короткоживущего состояния.

### 3.2 Рекомендуемый стек

- [ ] **Использовать Open WebUI как основной frontend/UI-слой.**
  
  **Контекст:** Open WebUI даёт готовый интерфейс, knowledge-интеграцию, модели, tools/functions/pipes и снижает стоимость поддержки фронта.

- [ ] **Использовать Qdrant как основной первый кандидат на vector DB.**
  
  **Контекст:** подходит для плавной миграции, payload filters, multitenancy, document/thread filtering, hybrid retrieval. Milvus оставить как альтернативу для более тяжёлых multi-vector сценариев.

- [ ] **Использовать PostgreSQL как metadata storage.**
  
  **Контекст:** PostgreSQL должен хранить документы, версии, статусы ingestion, связи с чатами и thread scope, а не только operational логику.

- [ ] **Использовать отдельный embedding service.**
  
  **Контекст:** эмбеддер не должен быть жёстко зашит в UI. Он должен вызываться ingestion- и retrieval-слоем независимо.

- [ ] **Использовать отдельный reranker service.**
  
  **Контекст:** reranker нужно встроить как отдельный шаг после initial retrieval и до генерации ответа.

- [ ] **Использовать Redis (опционально, но желательно) для кэширования и статусов фоновых задач.**
  
  **Контекст:** нужен для ingestion jobs, короткоживущего кеша retrieval и хранения прогресса обработки документов.

## 4. Принципы миграции

- [ ] **Запретить full rewrite “в один этап”.**
  
  **Контекст:** переход должен происходить поэтапно, с сохранением совместимости между текущим Chainlit-контуром и новым стеком.

- [ ] **Сначала перенести retrieval и storage, потом UI.**
  
  **Контекст:** самая критичная часть — убрать session-bound индекс и локальный retrieval state. После этого UI можно менять безопаснее.

- [ ] **Не удалять текущий routing-контур до тех пор, пока его поведение не будет воспроизведено в новом orchestration service.**
  
  **Контекст:** UI может смениться, но поведение системы должно сохраняться.

- [ ] **Сделать новую систему обратно совместимой на период перехода.**
  
  **Контекст:** старый Chainlit должен иметь возможность вызывать уже новый ingestion/retrieval backend на промежуточном этапе.

## 5. Логическое разделение состояния

- [ ] **Разделить chat/session state, document state и retrieval state.**
  
  **Контекст:** это ключевой архитектурный шаг. Нельзя хранить всё в памяти UI-сессии.

### 5.1 Chat / Session state

- [ ] **В chat/session state хранить только историю диалога, активный режим и ссылки на активные документы.**
  
  **Контекст:** чат должен хранить “что сейчас прикреплено”, но не весь retrieval-индекс.

### 5.2 Document state

- [ ] **Каждому документу присваивать устойчивые идентификаторы.**
  
  **Контекст:** минимум нужны:
  - `document_id`
  - `tenant_id`
  - `thread_id` или `workspace_id`
  - `version_id`
  - `file_hash`
  - `source_type`
  - `ingestion_status`

- [ ] **Хранить версии документа отдельно.**
  
  **Контекст:** переиндексация и повторная загрузка должны быть привязаны к версии, а не ломать все старые ссылки.

### 5.3 Retrieval state

- [ ] **Retrieval state хранить в vector DB + metadata DB, а не в runtime памяти UI.**
  
  **Контекст:** при рестарте или horizontal scaling система должна продолжать находить документы без потери индекса.

## 6. Целевая схема данных

### 6.1 Metadata DB (PostgreSQL)

- [ ] **Создать таблицу `users`.**
  
  **Контекст:** пользовательская идентификация, multitenancy и контроль доступа.

- [ ] **Создать таблицу `threads` / `chats`.**
  
  **Контекст:** связь между UI-чатами и retrieval scope.

- [ ] **Создать таблицу `documents`.**
  
  **Контекст:** базовая сущность документа независимо от версии.

- [ ] **Создать таблицу `document_versions`.**
  
  **Контекст:** hash, размер, mime type, parser version, embedding model version, status ingestion.

- [ ] **Создать таблицу `document_bindings`.**
  
  **Контекст:** какие документы прикреплены к каким chat/thread/workspace.

- [ ] **Создать таблицу `ingestion_jobs`.**
  
  **Контекст:** состояние пайплайна загрузки: pending / processing / indexed / failed.

- [ ] **Создать таблицу `retrieval_audit_log` (опционально, но желательно).**
  
  **Контекст:** пригодится для диагностики, оценки качества и последующей аналитики retrieval.

### 6.2 Vector DB payload schema

- [ ] **Для каждого чанка хранить нормализованный payload.**
  
  **Контекст:** минимум нужны поля:
  - `tenant_id`
  - `document_id`
  - `version_id`
  - `thread_id` / `workspace_id`
  - `source_scope` (`session`, `knowledge_base`, `overlay`)
  - `section_title`
  - `chunk_index`
  - `language`
  - `created_at`
  - `doc_type`
  - `tags`

- [ ] **Поддержать фильтрацию retrieval по payload.**
  
  **Контекст:** это база для вопросов “по этому документу”, “по этим двум документам”, “по KB этого workspace”, “по документам текущей сессии”.

## 7. Документный ingestion pipeline

- [ ] **Выделить ingestion в отдельный сервис/воркер.**
  
  **Контекст:** загрузка документа не должна блокировать chat runtime.

### 7.1 Шаги ingestion

- [ ] **Реализовать нормализованный этап загрузки файла.**
  
  **Контекст:** после загрузки файл должен попадать в storage и регистрироваться как `document_version`.

- [ ] **Реализовать извлечение текста и структурных элементов.**
  
  **Контекст:** парсер должен поддерживать хотя бы PDF, DOCX, TXT, Markdown, HTML. Желательно предусмотреть расширение под таблицы и OCR-сценарии отдельно.

- [ ] **Сохранить и адаптировать текущую секционно-ориентированную chunking-логику.**
  
  **Контекст:** текущий chunker уже умеет уважать структуру документа. Это нужно перенести в новый ingestion pipeline как отдельный модуль, а не заменить на примитивный fixed-size chunking.

- [ ] **Добавить стратегию chunking по типам документа.**
  
  **Контекст:** юридические документы, регламенты, статьи, инструкции и markdown-заметки лучше резать по-разному.

- [ ] **Добавить нормализацию метаданных чанков.**
  
  **Контекст:** section, subsection, page, paragraph, source path, doc type — всё это нужно сохранять для точной цитируемости.

- [ ] **Реализовать генерацию dense embeddings.**
  
  **Контекст:** embedding model должна быть конфигурируемой, а версия эмбеддера — сохраняться в metadata DB.

- [ ] **При необходимости реализовать sparse representations / BM25-compatible indexing.**
  
  **Контекст:** hybrid retrieval должен поддерживаться не только через dense-only поиск.

- [ ] **Индексировать чанки в vector DB.**
  
  **Контекст:** запись должна быть идемпотентной и привязанной к `document_version`.

- [ ] **Обновлять ingestion status после каждого этапа.**
  
  **Контекст:** UI и backend должны видеть, готов документ к поиску или ещё в обработке.

### 7.2 Требования к устойчивости ingestion

- [ ] **Сделать ingestion идемпотентным.**
  
  **Контекст:** повторная загрузка одного и того же файла не должна создавать мусорные дубликаты без контроля.

- [ ] **Добавить дедупликацию по hash + tenant scope.**
  
  **Контекст:** это предотвратит хаос при повторных загрузках.

- [ ] **Добавить повторный запуск failed jobs.**
  
  **Контекст:** документ не должен требовать ручного восстановления БД при временной ошибке.

## 8. Retrieval слой

- [ ] **Вынести retrieval в отдельный backend-модуль/сервис.**
  
  **Контекст:** retrieval должен вызываться одинаково и из Chainlit на этапе миграции, и из Open WebUI после миграции.

### 8.1 Retrieval режимы

- [ ] **Сохранить поддержку как минимум трёх retrieval scope-режимов:**
  - только документы текущей сессии;
  - только knowledge base;
  - knowledge base + session overlay.
  
  **Контекст:** это уже соответствует текущей логике и должно остаться в новом стеке.

- [ ] **Реализовать retrieval по filters вместо in-memory active pipeline rebuild.**
  
  **Контекст:** вместо пересоздания индекса по активным документам runtime должен выполнять запрос в vector DB с фильтрами по `tenant_id`, `thread_id`, `document_ids`, `source_scope`.

### 8.2 Retrieval pipeline

- [ ] **Реализовать первичный candidate retrieval.**
  
  **Контекст:** dense retrieval + optional sparse retrieval / BM25 / hybrid.

- [ ] **Реализовать fusion-слой.**
  
  **Контекст:** RRF или аналог должен объединять dense и sparse кандидатов.

- [ ] **Реализовать post-filtering по metadata.**
  
  **Контекст:** фильтрация по документам, языку, типу документа, дате, scope.

- [ ] **Реализовать reranking top-N кандидатов.**
  
  **Контекст:** после initial retrieval кандидаты должны пересортировываться более точной моделью.

- [ ] **Реализовать формирование context pack для LLM.**
  
  **Контекст:** в LLM должен идти не просто текст чанков, а нормализованный набор evidence blocks с метаданными и возможностью ссылки на источник.

### 8.3 Рекомендуемая стратегия retrieval

- [ ] **Использовать hybrid retrieval как дефолт.**
  
  **Контекст:** dense-only режим не должен быть единственным рабочим сценарием.

- [ ] **Оставить query expansion как optional corrective шаг.**
  
  **Контекст:** текущий Rocchio-like corrective retrieval можно оставить как fallback, но не как центральный механизм качества.

- [ ] **Перенести текущую эвристику confidence в post-retrieval guardrail слой.**
  
  **Контекст:** confidence/groundedness должна остаться, но как вспомогательный валидатор поверх retrieval+rereank, а не как замена качественному ranker.

## 9. Reranker слой

- [ ] **Добавить отдельный reranker как обязательный прод-слой.**
  
  **Контекст:** текущих эвристик и z-score grading недостаточно для долгой устойчивой работы retrieval.

- [ ] **Сделать reranker конфигурируемым.**
  
  **Контекст:** модель должна быть заменяемой без переписывания pipeline.

- [ ] **На первом этапе поддержать минимум 2 профиля:**
  - lightweight profile;
  - quality profile.
  
  **Контекст:** это позволит балансировать между скоростью и качеством.

- [ ] **Ограничить rerank до top-N кандидатов.**
  
  **Контекст:** reranker не должен гоняться по всему индексу; он нужен для точной перестановки shortlist.

- [ ] **Логировать score до и после rerank.**
  
  **Контекст:** пригодится для оценки реального выигрыша качества.

---

## 10. Оркестрация и роутинг

- [ ] **Сохранить текущий routing как отдельный orchestration service.**
  
  **Контекст:** Open WebUI не должен “магически” заменить твою прикладную логику маршрутизации.

### 10.1 Что должен делать orchestration layer

- [ ] **Определять тип запроса.**
  
  **Контекст:** общий чат, вопрос по документу, summary, compare, knowledge-base query, equipment analysis, служебный режим.

- [ ] **Определять retrieval scope.**
  
  **Контекст:** session docs, KB, смешанный режим.

- [ ] **Определять активные документы и document binding для конкретного thread/chat.**
  
  **Контекст:** если пользователь спрашивает “по этому документу”, orchestration должен понимать, какой именно набор документов относится к контексту чата.

- [ ] **Выбирать пайплайн ответа.**
  
  **Контекст:** direct LLM, RAG answer, summary workflow, compare workflow и др.

- [ ] **Собирать итоговый prompt/context для LLM.**
  
  **Контекст:** orchestration — это не только классификация, но и финальная сборка запроса к модели.

- [ ] **Обрабатывать fallback и low-confidence ответы.**
  
  **Контекст:** если evidence слабый, нужно уметь либо честно сузить ответ, либо попросить пользователя уточнить документ/область без ложной уверенности.

### 10.2 Как встроить orchestration в Open WebUI

- [ ] **Реализовать orchestration как внешний API / pipeline service.**
  
  **Контекст:** Open WebUI должен обращаться к нему через Pipes/Functions, а не хранить всю сложную логику внутри UI-конфигурации.

- [ ] **Сделать orchestration backend независимым от конкретного UI.**
  
  **Контекст:** это оставит возможность использовать тот же backend из Chainlit, Open WebUI или другого клиента.

## 11. Работа с сессией и документами в чате

- [ ] **Ввести модель “attached documents” для каждого thread/chat.**
  
  **Контекст:** чат должен знать, какие документы считаются активными для ответов.

- [ ] **Сохранять список активных документов в metadata DB.**
  
  **Контекст:** активность документа не должна теряться при рестарте UI.

- [ ] **Реализовать явные операции attach / detach / activate / deactivate document.**
  
  **Контекст:** пользователь и система должны управлять тем, какие документы реально участвуют в retrieval.

- [ ] **Добавить политику выбора scope по умолчанию.**
  
  **Контекст:** например:
  - если в чате есть активные документы, сначала искать в них;
  - затем при необходимости расширяться в KB;
  - либо использовать отдельный режим “только этот документ”.

- [ ] **Сделать поддержку overlay для новых документов до полного ingestion в общую KB.**
  
  **Контекст:** freshly uploaded files должны стать доступны в вопросах как можно раньше, но без нарушения общей архитектуры.

---

## 12. Ответы, цитирование и evidence layer

- [ ] **Реализовать нормализованный evidence format.**
  
  **Контекст:** каждый кусок контекста должен содержать `document_id`, `version_id`, `section`, `page`, `chunk_id`, `score`.

- [ ] **Добавить обязательную привязку ответа к evidence blocks для document QA.**
  
  **Контекст:** вопросы по документам должны по умолчанию быть grounded.

- [ ] **Реализовать цитирование источников в ответе.**
  
  **Контекст:** пользователь должен видеть, из какого документа и из какого раздела система взяла утверждение.

- [ ] **Добавить режим graceful degradation.**
  
  **Контекст:** если retrieval слабый, система должна отвечать аккуратно: “не нашёл точного подтверждения”, а не галлюцинировать.

---

## 13. Модели и конфигурация

- [ ] **Вынести все модели в конфиг.**
  
  **Контекст:** LLM, embedding model, reranker, classifier должны быть заменяемыми через конфигурацию.

- [ ] **Разделить runtime-профили.**
  
  **Контекст:** нужен хотя бы такой набор:
  - dev;
  - local-light;
  - production-balanced;
  - production-quality.

- [ ] **Предусмотреть отключаемость тяжёлых модулей.**
  
  **Контекст:** reranker, corrective retrieval и некоторые классификаторы должны иметь feature flags.

---

## 14. Open WebUI integration requirements

- [ ] **Поднять Open WebUI как отдельный сервис, а не как место хранения всех данных системы.**
  
  **Контекст:** UI не должен быть единственным source of truth для документационного состояния.

- [ ] **Настроить внешнее shared storage для production deployment.**
  
  **Контекст:** файлы, документы и метаданные не должны жить только в локальном контейнере UI.

- [ ] **Настроить интеграцию Open WebUI с внешним orchestration backend через Pipes или Functions.**
  
  **Контекст:** пользователь выбирает модель/режим в Open WebUI, а реальная логика идёт во внешний backend.

- [ ] **Настроить пользовательские режимы/модели в Open WebUI под существующие use-cases.**
  
  **Контекст:** например:
  - General Chat
  - Document QA
  - KB Search
  - Summary
  - Compare Docs

## 16. Технические требования к качеству

- [ ] **Время ответа для стандартного document QA должно быть предсказуемым и ограниченным SLA.**
  
  **Контекст:** нужен отдельный бюджет времени на retrieval, rerank и generation.

- [ ] **Система должна переживать рестарт без потери доступности ранее загруженных документов.**
  
  **Контекст:** это один из главных критериев того, что миграция удалась.

- [ ] **Система должна поддерживать multi-user и multi-thread режим без смешивания документов между пользователями.**
  
  **Контекст:** multitenancy и access isolation обязательны.

- [ ] **Система должна поддерживать горизонтальное масштабирование UI и backend-слоёв.**
  
  **Контекст:** Open WebUI и orchestration backend должны масштабироваться независимо.

## 19. Что разрешено переиспользовать из текущего кода

- [ ] **Переиспользовать концепцию hybrid retrieval.**
  
  **Контекст:** dense + sparse + fusion — правильное направление, его не нужно выкидывать.

- [ ] **Переиспользовать текущий доменно-ориентированный chunking.**
  
  **Контекст:** это одна из наиболее ценных частей текущей реализации.

- [ ] **Переиспользовать routing-логику как основу orchestration service.**
  
  **Контекст:** это бизнес-логика продукта, а не случайная техническая деталь.

- [ ] **Переиспользовать confidence/fallback как вспомогательный guardrail.**
  
  **Контекст:** но не оставлять его единственным механизмом оценки качества retrieval.

## 20. Что необходимо заменить или убрать

- [ ] **Убрать зависимость от session-only pipeline cache как источника правды.**
  
  **Контекст:** это допустимо только как временный runtime cache, но не как основа retrieval.

- [ ] **Убрать хранение долговременной knowledge base в локальном SQLite как основном retrieval backend.**
  
  **Контекст:** SQLite можно оставить разве что для локального dev-режима, но не как production retrieval store.

- [ ] **Убрать иллюзию “agentic retrieval”, если под ним скрыт просто corrective loop.**
  
  **Контекст:** в новой архитектуре режимы должны быть названы честно и соответствовать реальному поведению.

## 21. Критерии приёмки

- [ ] **Пользователь может загрузить документ в Open WebUI и получить ответ именно по нему после рестарта системы.**

- [ ] **Пользователь может вести чат по нескольким прикреплённым документам без пересборки in-memory индекса на каждый запрос.**

- [ ] **Система различает scope: текущий документ, документы текущего чата, вся KB.**

- [ ] **Ответы по документам содержат evidence/citations.**

- [ ] **Routing нового backend повторяет ключевые сценарии текущей Chainlit-логики.**

- [ ] **Open WebUI работает как основной пользовательский интерфейс без потери core-функций.**

- [ ] **Chainlit может быть отключён без потери доступа к уже проиндексированным документам и knowledge base.**

## 22. Рекомендуемый минимальный MVP новой архитектуры

- [ ] **Open WebUI** как UI.
- [ ] **PostgreSQL** как metadata DB.
- [ ] **Qdrant** как vector DB.
- [ ] **Отдельный ingestion worker**.
- [ ] **Отдельный orchestration API**.
- [ ] **Hybrid retrieval + reranker**.
- [ ] **Document binding по thread/chat**.
- [ ] **Citations/evidence в ответе**.

**Контекст:** этого достаточно, чтобы перейти от прототипного session-bound RAG к устойчивой рабочей архитектуре без немедленного усложнения GraphRAG, multi-agent и других тяжёлых сценариев.

## 24. Итоговая рекомендация по реализации

- [ ] **Реализовать миграцию как переход от “самописного RAG внутри UI” к “слоистой продуктовой архитектуре вокруг Open WebUI”.**
  
  **Контекст:** итоговая система должна выглядеть так:
  - Open WebUI = интерфейс;
  - внешний orchestration backend = логика и роутинг;
  - ingestion worker = обработка документов;
  - Qdrant/Milvus = retrieval backend;
  - PostgreSQL = метаданные и bindings;
  - reranker = quality layer.

- [ ] **Считать успешной миграцией не сам факт перехода на другой UI, а исчезновение зависимости от session-bound retrieval и появление устойчивого document-aware backend.**
  
  **Контекст:** именно это является главным техническим смыслом всего перехода.
