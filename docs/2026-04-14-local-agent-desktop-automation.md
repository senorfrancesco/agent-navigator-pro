# Локальная автоматизация настольных приложений для CLI-агентов

Этот документ фиксирует, как в текущей сессии агент управлял `Telegram Desktop` на локальной Linux-машине, какие команды и механизмы для этого использовались, и как такой же подход можно оформить в виде локальных инструментов для CLI-агентов, включая локальный стек на `Qwen` с `16 GB VRAM`.

## Короткий вывод

Ключевая идея проста:

- модель не должна «магически» уметь нажимать кнопки;
- модель должна вызывать маленькие локальные инструменты;
- инструменты должны делать детерминированные действия: открыть приложение, найти окно, снять скриншот, кликнуть, вставить текст, проверить результат;
- каждое рискованное действие должно подтверждаться отдельно: отправка сообщения, звонок, удаление, подтверждение диалога.

В этой сессии работал не «универсальный GUI-агент», а практический конвейер:

1. найти приложение и окно;
2. получить доступ к экрану `X11`;
3. сделать снимок окна;
4. прочитать интерфейс глазами агента;
5. ввести текст через буфер обмена и синтетические события клавиатуры и мыши;
6. снова сделать снимок и проверить, что действие реально произошло.

Именно такой цикл удобнее всего переносить в локальные инструменты для `Qwen` или любого другого CLI-агента.

## Что именно было сделано в этой сессии

Последовательность действий была такой:

1. Проверка наличия `Telegram Desktop` и поиск локального `.desktop`-файла.
2. Проверка браузерного пути через `Telegram Web` на случай, если нативного клиента нет или он не авторизован.
3. Запуск нативного клиента `Telegram`.
4. Поиск и идентификация окна `Telegram` через `X11`.
5. Снятие скриншота окна через `ffmpeg` и визуальная проверка списка чатов.
6. Поиск нужного контакта через поле поиска.
7. Открытие чата найденного контакта.
8. Вставка текста сообщения через буфер обмена и отправка.
9. Повторная проверка статуса сообщения по скриншоту.
10. Попытка голосового вызова через окно звонка `Telegram`.
11. Проверка, был ли ответ на звонок, и чтение статуса чата.

## Использованные инструменты верхнего уровня

На уровне агентной среды использовались такие примитивы:

- `functions.exec_command`
  - запуск локальных команд и небольших Python-скриптов;
- `multi_tool_use.parallel`
  - параллельный сбор контекста, например поиск бинарника, `.desktop`-файлов и доступных утилит;
- `mcp__playwright__browser_*`
  - для проверки `Telegram Web`;
- `functions.view_image`
  - просмотр локально сохранённых скриншотов;
- `web`
  - не для управления `Telegram`, а для проверки официальных карточек моделей `Qwen` при рекомендациях по локальному стеку.

На уровне самой машины использовались:

- `xwininfo`
  - получить список окон и размеры;
- `ffmpeg -f x11grab`
  - снять скриншот окна или части экрана;
- `xclip`
  - положить русский текст в буфер обмена;
- `python3` + `ctypes` + `libX11.so.6` + `libXtst.so.6`
  - сфокусировать окно, кликать мышью, посылать клавиши и сочетания;
- `Pillow`
  - вырезать увеличенные фрагменты скриншота для проверки галочек и статусов.

## Команды, которые реально запускались

Ниже не абстрактные примеры, а команды и приёмы того же типа, которые реально использовались в текущей сессии.

### 1. Поиск приложения

```bash
command -v telegram || command -v Telegram || command -v telegram-desktop || true
```

```bash
rg -n "Telegram|telegram" /usr/share/applications ~/.local/share/applications --glob '*.desktop'
```

```bash
test -x '/home/seral/Загрузки/Telegram/Telegram' && echo EXISTS || echo MISSING
```

Результат: был найден локальный запускатель `Telegram` в `'/home/seral/Загрузки/Telegram/Telegram'`.

### 2. Запуск приложения

```bash
'/home/seral/Загрузки/Telegram/Telegram'
```

Это действие требовало доступа вне песочницы, потому что речь шла о запуске GUI-приложения.

### 3. Поиск окна `Telegram`

Внутри песочницы доступ к `DISPLAY` был закрыт, поэтому запрос пришлось выполнять с повышенными правами:

```bash
xwininfo -root -tree | rg -i 'telegram|Telegram'
```

По выводу было видно:

- окно главного чата;
- отдельные служебные окна `TelegramDesktop`;
- позже окно модального звонка.

### 4. Снятие скриншота окна

Вместо отдельного средства для скриншотов использовался `ffmpeg`:

```bash
ffmpeg -y -f x11grab -video_size 1920x1048 -i :1+0,32 -frames:v 1 /tmp/telegram-window.png
```

Этот приём дал:

- полный снимок окна `Telegram`;
- возможность передать изображение агенту для визуальной проверки;
- воспроизводимый путь без привязки к конкретной оболочке рабочего стола.

### 5. Вставка текста в поиск и в поле сообщения

Сначала текст помещался в буфер обмена:

```bash
DISPLAY=:1 xclip -selection clipboard -in <<< 'Данила Менделев'
```

Потом запускался Python-скрипт, который:

- открывал `DISPLAY=:1`;
- выбирал главное окно `Telegram`;
- вызывал `XRaiseWindow`;
- вызывал `XSetInputFocus`;
- синтезировал движение мыши через `XTestFakeMotionEvent`;
- синтезировал клик через `XTestFakeButtonEvent`;
- вставлял текст через `Ctrl+V` с `XTestFakeKeyEvent`.

По той же схеме отправлялось и сообщение.

### 6. Проверка, что действие реально произошло

После каждой рискованной операции снова делался снимок экрана:

```bash
ffmpeg -y -f x11grab -video_size 1920x1048 -i :1+0,32 -frames:v 1 /tmp/telegram-danik-sent.png
```

Если нужно было проверить мелкий элемент, снимок обрезался:

```python
from PIL import Image
img = Image.open('/tmp/telegram-danik-sent.png')
crop = img.crop((980, 850, 1500, 1010))
crop.save('/tmp/telegram-danik-sent-crop.png')
```

Это позволило проверить:

- одну или две галочки;
- появился ли ответ;
- сменился ли статус на `был(а) недавно`;
- начался ли звонок;
- закончился ли звонок как `Отменённый звонок`.

## Почему этот подход сработал

Сработало сочетание трёх факторов:

### 1. Это был `X11`, а не жёстко ограниченный `Wayland`

В сессии был доступен `DISPLAY=:1`, и окно можно было увидеть через `xwininfo`. Это важно, потому что:

- на `X11` реально синтезировать мышь и клавиатуру на уровне системы;
- на `Wayland` этот путь обычно либо закрыт, либо требует отдельного слоя доступа.

### 2. Использовались маленькие проверяемые шаги

Вместо одной команды «найди человека и позвони ему» использовался цикл:

1. выполнить действие;
2. сделать снимок;
3. визуально проверить;
4. только потом идти дальше.

Это сильно снижает число ложных срабатываний.

### 3. Русский текст не печатался посимвольно

Для русского текста надёжнее:

- положить строку в буфер обмена;
- вставить её через `Ctrl+V`.

Иначе придётся зависеть от раскладки, `XKB` и преобразования символов в `keysym`.

## Как превратить это в локальные инструменты для CLI-агентов

Практический вариант: не шить всю логику внутрь агента, а вынести её в локальный `tool server`.

Лучший формат для этого — отдельный локальный сервер инструментов по `MCP` или хотя бы JSON-RPC по `stdio`.

### Рекомендуемый слой примитивов

Сначала стоит вынести универсальные инструменты рабочего стола:

- `desktop.launch_app`
- `desktop.list_windows`
- `desktop.focus_window`
- `desktop.capture_screen`
- `desktop.capture_window`
- `desktop.click`
- `desktop.double_click`
- `desktop.press_keys`
- `desktop.type_text`
- `desktop.set_clipboard`
- `desktop.wait`
- `desktop.crop_image`
- `desktop.ocr_image`

Потом поверх них можно сделать прикладные инструменты:

- `telegram.search_contact`
- `telegram.open_chat`
- `telegram.send_message`
- `telegram.read_last_message_status`
- `telegram.start_call`
- `telegram.read_chat_presence`

### Почему лучше два слоя, а не один большой инструмент

Если сделать один инструмент `telegram_do_everything`, получится плохо:

- модель не сможет аккуратно восстанавливаться после ошибки;
- не будет нормальной промежуточной проверки;
- труднее вводить подтверждения;
- сложнее журналировать действия.

Если же держать два слоя, можно:

- использовать общие примитивы для любых приложений, а не только `Telegram`;
- добавлять прикладные обёртки только там, где это действительно нужно;
- отдельно подтверждать опасные действия.

## Предлагаемая архитектура локального набора инструментов

```text
CLI agent
  -> MCP client
  -> local desktop tool server
       -> backend.x11
       -> backend.screenshot
       -> backend.clipboard
       -> backend.ocr
       -> app.telegram
```

### Модули

```text
tools/
  desktop_server.py
  backends/
    x11_backend.py
    screenshot_backend.py
    clipboard_backend.py
    ocr_backend.py
  apps/
    telegram_tools.py
```

### Что делает каждый модуль

- `x11_backend.py`
  - список окон, фокус, клики, клавиши, чтение геометрии окна;
- `screenshot_backend.py`
  - полный снимок, снимок окна, снимок прямоугольника;
- `clipboard_backend.py`
  - установка и чтение буфера обмена;
- `ocr_backend.py`
  - извлечение текста из снимка;
- `telegram_tools.py`
  - сценарии поверх примитивов, например поиск контакта и отправка сообщения.

## Минимальный контракт инструментов

Инструменты должны возвращать не только `ok`, но и полезный контекст.

Пример:

```json
{
  "ok": true,
  "window_id": "0x1e00019",
  "title": "Даник Менделев",
  "x": 0,
  "y": 32,
  "width": 1920,
  "height": 1048
}
```

Для снимка:

```json
{
  "ok": true,
  "path": "/tmp/telegram-window.png",
  "window_id": "0x1e00019"
}
```

Для рискованного действия:

```json
{
  "ok": true,
  "action": "telegram.send_message",
  "target": "Даник Менделев",
  "requires_confirmation": true
}
```

## Что лучше использовать в качестве технической базы

### Для Linux и `X11`

Самый практичный набор:

- `python3`
- `ctypes` для `libX11` и `libXtst`
- `ffmpeg` или `scrot`
- `xclip`
- `Pillow`
- `tesseract` или другой `OCR`, если нужно читать интерфейс автоматически

Если есть `xdotool`, можно строить систему ещё быстрее.  
Но в этой сессии его не было, поэтому использовался более низкий уровень через `XTest`.

### Для `Wayland`

Нужно сразу закладывать отдельный путь:

- `xdotool` и прямой `XTest` часто не помогут;
- нужен либо `xdg-desktop-portal`, либо слой специальных прав доступа, либо привязка к возможностям конкретного окружения рабочего стола.

Если нужна надёжная переносимость, удобнее иметь два backend:

- `x11_backend`;
- `wayland_backend`.

## Как это обыграть с локальным `Qwen` на `16 GB VRAM`

Главная мысль: на такой машине лучше не пытаться посадить на одну модель и агентное планирование, и полноценное зрение, и тяжёлую генерацию.

### Практичный вариант, который я бы рекомендовал первым

Использовать:

- текстовую модель для оркестрации действий;
- детерминированные локальные инструменты для рабочего стола;
- `OCR` для чтения интерфейса;
- скриншоты как артефакты в цикле проверки.

То есть не «зрение как магия», а «зрение как OCR + целевые снимки + правила».

Это лучший старт для `16 GB VRAM`, потому что:

- меньше нагрузка на память;
- меньше задержка;
- меньше неустойчивости;
- проще отлаживать.

### Рекомендованная конфигурация

Вариант А, базовый и наиболее реалистичный:

- `Qwen/Qwen2.5-Coder-7B-Instruct-AWQ` или `Qwen/Qwen2.5-Coder-14B-Instruct-GGUF`
- локальный `tool server`
- `OCR`
- `ffmpeg` и `X11`-backend

Вариант Б, если очень хочется разбирать скриншоты моделью, а не только `OCR`:

- текстовый оркестратор `Qwen/Qwen2.5-Coder-14B-Instruct-GGUF`
- отдельный визуальный помощник `Qwen/Qwen2.5-VL-7B-Instruct`
- запуск визуальной модели только по требованию, а не постоянно

### Почему я не рекомендую сразу строить всё на `VL`

На `16 GB VRAM` это обычно плохой первый шаг:

- зрительная модель съедает память, которую лучше отдать планировщику или контексту;
- простой интерфейс `Telegram` чаще выгоднее читать через `OCR`, а не через тяжёлую мультимодальную модель;
- надёжность достигается не моделью, а повторяемыми инструментами и снимками до и после действия.

### Практический вывод по памяти

Оценка ниже — это инженерный вывод из размера модели и типа квантизации, а не обещание из model card:

- `7B` в `AWQ/GGUF` обычно реалистичен для локального запуска на `16 GB VRAM`;
- `14B` в квантизованном виде тоже реалистичен, но уже с меньшим запасом;
- держать одновременно тяжёлый `14B` оркестратор и полноценный `VL 7B` в постоянной готовности на `16 GB VRAM` уже менее комфортно;
- поэтому лучший практический дизайн — текстовая модель постоянно, визуальная модель по требованию или вообще без неё.

Для ориентира: официальная карточка `Qwen/Qwen2.5-Coder-14B-Instruct-GGUF` публикует размеры файлов квантования порядка:

- `Q4_K_M` около `8.99 GB`;
- `Q5_K_M` около `10.5 GB`;
- `Q8_0` около `15.7 GB`.

Из этого следует практический вывод:

- `Q4` и `Q5` оставляют запас под окружение и инструменты;
- `Q8` уже почти съедает весь бюджет `16 GB`, поэтому для настольного агента это обычно не лучший режим;
- отдельную визуальную модель лучше запускать по требованию или вынести в другой процесс и не держать постоянно активной.

## Что я бы сделал для `Qwen` как реальный MVP

Если цель — повторить сегодняшние действия локально, я бы делал MVP так:

1. Поднять `Qwen` как текстовый агент-планировщик.
2. Поднять локальный `MCP`-сервер настольных инструментов.
3. Сделать только 8-10 надёжных инструментов, не больше.
4. Все опасные действия перевести в режим подтверждения.
5. Обязательно сохранять снимок окна до и после действия.
6. Для чтения статусов использовать `OCR` и вырезанные фрагменты окна.

Минимальный набор инструментов для MVP:

- `list_windows`
- `focus_window`
- `capture_window`
- `set_clipboard`
- `click`
- `press_hotkey`
- `wait`
- `crop_image`
- `ocr_image`
- `confirm_action`

Этого уже достаточно для:

- открыть `Telegram`;
- найти чат;
- отправить сообщение;
- проверить галочки;
- прочитать статус контакта;
- запустить звонок.

## Что важно для безопасности

Такие инструменты мощные, поэтому без ограничений их лучше не запускать.

Я бы добавил:

- белый список приложений, с которыми агенту можно работать;
- белый список действий высокого риска;
- обязательное подтверждение на `send`, `call`, `delete`, `confirm dialog`;
- журнал действий со скриншотами;
- режим `dry-run`, в котором агент показывает, что он собирается делать;
- ограничение по частоте ввода и кликов;
- отдельный системный пользователь для агентных автоматизаций.

## Ограничения и слабые места подхода

- Координаты хрупкие и зависят от геометрии окна.
- `Wayland` усложняет или запрещает часть механики.
- Скриншоты не равны структурированному дереву интерфейса.
- Без `OCR` или визуальной модели агент будет плохо читать мелкие статусы.
- Любое всплывающее окно может сбить сценарий, если после действия нет повторной проверки.

Поэтому правильный подход не «жать на память», а:

1. действие;
2. новый снимок;
3. проверка;
4. следующее действие.

## Рекомендуемый маршрут внедрения в этом репозитории

Если делать это внутри текущего проекта, я бы не встраивал такой слой в модельный код напрямую.

Лучше вынести его как отдельный локальный сервис инструментов:

- либо как отдельный `MCP`-сервер;
- либо как локальный Python-процесс с `stdio`-протоколом.

Такой сервер потом сможет использовать:

- `Codex`;
- `Qwen`;
- `Open WebUI`;
- любой другой локальный агент, умеющий звать внешние инструменты.

## Готовые аналоги `Codex` и `Claude Code` с локальными моделями

Если вопрос не в том, чтобы писать всё с нуля, а в том, можно ли взять уже существующий агентный CLI и посадить его на локальную модель, то ответ: да, но с разными компромиссами.

Важно разделять два класса решений:

- почти «готовая замена» `Codex` или `Claude Code`;
- терминальный агент, который можно приспособить под локальную модель, но он не повторяет их поведение один в один.

### 1. `OpenCode`

Это один из самых близких по духу вариантов к современному coding-agent CLI:

- есть терминальный интерфейс;
- есть режимы `Build` и `Plan`;
- есть встроенные subagents;
- есть `AGENTS.md`;
- есть совместимость с файлами и привычками `Claude Code`.

Что важно для локальных моделей:

- официальная документация пишет, что `OpenCode` поддерживает локальные модели;
- провайдеры можно заводить через `OpenAI-compatible` endpoint;
- в документации есть прямой пример локального провайдера через `LM Studio` на `http://127.0.0.1:1234/v1`;
- в актуальной документации среди моделей, которые «хорошо работают» с `OpenCode`, прямо упоминается `Qwen3 Coder`.

Практический смысл:

- если нужен интерфейс, похожий на `Claude Code`, это один из самых интересных кандидатов;
- для локального стека удобно поднять `LM Studio`, `vLLM` или другой `OpenAI-compatible` сервер и подать его в `OpenCode` как провайдера;
- под сильную локальную модель это, вероятно, лучший путь из готовых CLI-вариантов.

Практическое ограничение из официальных docs тоже важно:

- `OpenCode` прямо пишет, что только часть моделей хорошо справляется одновременно и с кодом, и с `tool calling`.

То есть формально локальные модели поддерживаются, но реально комфортный режим зависит от силы модели.

### 2. `Crush`

`Crush` от `Charm` тоже очень близок к классу «терминальный coding agent»:

- терминальный интерфейс;
- поддержка `MCP`;
- поддержка `AGENTS.md`;
- поддержка навыков (`skills`);
- гибкая конфигурация провайдеров и разрешений.

Для локальных моделей у него хороший базовый путь:

- он поддерживает кастомные `OpenAI-compatible` провайдеры;
- в `README` есть прямые примеры для `Ollama`;
- там же есть прямые примеры для `LM Studio`;
- значит локальный `Qwen` можно подать туда как обычный совместимый API endpoint.

Почему это интересно:

- `Crush` хорошо подходит, если хочется собственный стек инструментов и `MCP`-серверов;
- по духу он ближе к «собираем свою агентную рабочую станцию», чем к жёстко заданному продукту;
- для локальной модели это удобно, потому что вся интеграция строится вокруг совместимого API.

Но по интернет-источникам видно и практическое предупреждение:

- в issue tracker есть реальные кейсы, где совместимость `MCP` и `OpenAI-compatible` схем требует дополнительных обходов;
- то есть это мощный вариант, но иногда более инженерный, чем «всё работает из коробки».

### 3. `Goose`

`Goose` интересен тем, что это не просто coding CLI, а более общий локальный агент:

- он работает локально;
- умеет CLI и desktop workflows;
- строится вокруг расширений и инструментов;
- поддерживает внешние `MCP`-сервера;
- имеет отдельную документацию по локальным провайдерам.

Для локальных моделей официальный стек у него уже продуман:

- `Ollama`;
- `LM Studio`;
- `Docker Model Runner`;
- `Ramalama`.

В официальной документации есть прямой раздел `Local LLMs`, а в блоге есть отдельный материал про запуск `goose` вместе с `Ollama` для полностью локального режима.

Это делает `Goose` сильным кандидатом, если цель не только писать код, но и:

- работать с приложениями;
- автоматизировать shell и desktop;
- цеплять свои расширения;
- делать общий локальный агент, а не только редактор кода.

Но тут есть важное ограничение из docs:

- `Goose` сильно опирается на `tool calling`;
- модели без `tool calling` в штатном режиме могут только чатиться;
- для них у `Goose` есть экспериментальный `Ollama Tool Shim`, но он прямо помечен как experimental.

Иными словами:

- для сильной локальной модели с нормальным `tool calling` это хороший путь;
- для слабых или нестабильных моделей будет больше трения.

### 4. `Aider`

`Aider` не совсем «форк `Claude Code`», но это один из самых зрелых терминальных инструментов для правки кода с участием модели.

Что он умеет:

- работать внутри git-репозитория;
- редактировать файлы;
- делать коммиты;
- работать через разные провайдеры;
- использовать локальные модели через `Ollama` или любой `OpenAI-compatible` API.

Официальная документация это подтверждает прямо:

- отдельная страница `Connecting to LLMs` говорит, что `Aider` умеет локальные модели;
- отдельная страница `Ollama` даёт рабочий сценарий запуска через `ollama serve` и `aider --model ollama_chat/<model>`.

Но у `Aider` есть и честное предупреждение в docs:

- если модель недостаточно сильная, она может «уметь отвечать кодом», но не справляться с правильным форматом редактирования файлов;
- docs прямо предупреждают, что слабые модели работают плохо.

Отсюда вывод:

- `Aider` отлично годится как локальный coding assistant;
- но если нужен именно агентный опыт уровня `Codex` с subagents, `MCP`, desktop tools и оркестрацией, он уже заметно уже по возможностям.

## Что из этого ближе всего к твоему запросу

Если задача звучит как:

> «Хочу что-то по ощущениям близкое к `Codex` или `Claude Code`, но чтобы мозг был локальный»

то я бы ранжировал варианты так:

### Лучший готовый кандидат

- `OpenCode`

Почему:

- ближе всего по UX и модели работы;
- есть `AGENTS.md`;
- есть режимы `Plan` и `Build`;
- есть subagents;
- есть совместимость с `Claude Code` conventions;
- есть официальный путь к локальным моделям через `LM Studio` и `OpenAI-compatible` провайдеры.

### Лучший конструктор агентной рабочей станции

- `Crush`

Почему:

- очень гибкий;
- хороший `MCP` story;
- умеет `AGENTS.md` и `skills`;
- локальные модели через `Ollama` и `LM Studio` конфигурируются явно.

### Лучший вариант для общего локального агента, не только для кода

- `Goose`

Почему:

- он изначально позиционируется как локальный агент;
- локальные провайдеры у него описаны в docs;
- он хорошо смотрится для сценариев «код + shell + desktop + внешние инструменты».

### Лучший практичный минимум, если важна надёжность редактирования

- `Aider`

Почему:

- зрелый;
- понятный;
- легко подключается к `Ollama`;
- даёт быстрый рабочий результат без лишней сложности.

## Что бы я рекомендовал конкретно для локального `Qwen`

Если ориентироваться на `Qwen` и машину с `16 GB VRAM`, я бы предложил три реалистичных сценария.

### Сценарий А, самый практичный

- `OpenCode` или `Crush`
- локальный `OpenAI-compatible` endpoint
- модель `Qwen` в квантизованном виде
- отдельный локальный `MCP`-сервер инструментов

Это лучший путь, если хочется максимально приблизиться к опыту `Codex` или `Claude Code`.

### Сценарий Б, если нужен упор на desktop automation

- `Goose`
- локальный `Ollama` или `LM Studio`
- отдельные desktop tools

Это лучше, если кодирование — только часть сценария, а не вся задача.

### Сценарий В, если нужен быстрый и простой старт

- `Aider`
- `Ollama`
- `Qwen` как локальная модель редактора

Это менее «агентно», но часто быстрее доводится до рабочего состояния.

## Честный вывод по рынку на сегодня

По текущим официальным источникам видно следующее:

- прямого локального аналога `Claude Code`, который уже стал общепринятым стандартом, пока нет;
- зато уже есть несколько сильных open-source агентов, которые умеют локальные модели через `Ollama`, `LM Studio` или `OpenAI-compatible` endpoint;
- главное узкое место — не сам CLI, а качество локальной модели именно в `tool calling`, удержании контекста и дисциплине редактирования.

То есть сегодня ограничение обычно такое:

- CLI и инструменты уже готовы;
- локальные endpoints уже готовы;
- `MCP` уже готов;
- а вот итоговое качество агентного поведения всё ещё сильно зависит от модели.

## Итог

Да, такой режим локально реализуем.

Но выигрывает не тот стек, где модель «умеет GUI», а тот, где:

- модель планирует;
- локальные инструменты делают маленькие детерминированные шаги;
- скриншоты и `OCR` используются как слой проверки;
- рискованные действия подтверждаются отдельно.

Для машины с `16 GB VRAM` я бы начинал не с тяжёлой мультимодальности, а с текстового `Qwen` + локальных desktop tools + `OCR`. Это даст самый высокий шанс быстро получить рабочий и отлаживаемый агент.
