# Памятка по разработке форка `Open WebUI`

Эта памятка нужна, чтобы не потеряться при работе сразу с двумя репозиториями:

- текущий продуктовый репозиторий: [agent-navigator-pro](/home/seral/HDD/proj/agent-navigator-pro)
- форк платформы: `/home/seral/HDD/proj/open-webui`

## 1. Кто за что отвечает

### `agent-navigator-pro`

Это главный репозиторий продукта. Здесь находится источник истины для:

- смешанного контура запуска;
- параметров контейнера `open-webui`;
- `tool_jobs`, `agent-api`, `document-server`, `legal-server`, `ums`;
- интеграционных тестов `Open WebUI` поверх нашего backend;
- `bootstrap_openwebui.py`, `Workspace Tools`, `Playwright`-контуров.

### `open-webui`

Это форк платформы, в котором мы меняем:

- серверный слой `Open WebUI`, если нужен прокси к `tool_jobs`;
- клиентский рендер сообщений, панелей и `Stop`;
- сериализацию `open_webui:deep_job`;
- постоянную панель вместо временного `bubble`.

Короткое правило:

- продуктовая интеграция и топология запуска живут в `agent-navigator-pro`;
- платформенные изменения интерфейса и слоя сообщений и выполнения живут в форке `open-webui`.

## 2. Что переносить из `agent-navigator-pro` во форк

При разработке форка мы не придумываем окружение заново, а повторяем рабочую политику контейнера `open-webui` из [docker-compose.yaml](../../docker-compose.yaml).

Сейчас для `open-webui` в продукте зафиксированы такие важные параметры:

```dotenv
OPENAI_API_BASE_URL=http://host.docker.internal:8000/v1
OPENAI_API_KEY=sk-dummy
ENABLE_FOLLOW_UP_GENERATION=False

HF_HUB_OFFLINE=1
ENABLE_RAG_WEB_SEARCH=False
ENABLE_RAG_LOCAL_WEB_FETCH=False

VECTOR_DB=qdrant
QDRANT_URI=http://qdrant:6333
ENABLE_QDRANT_MULTITENANCY_MODE=true
QDRANT_COLLECTION_PREFIX=anp-openwebui

RAG_EMBEDDING_ENGINE=openai
RAG_OPENAI_API_BASE_URL=http://host.docker.internal:8092/v1
RAG_OPENAI_API_KEY=sk-dummy
RAG_EMBEDDING_MODEL=qwen3-embedding-0.6b
RAG_RERANKING_ENGINE=

OPENWEBUI_SESSION_RAG_HANDOFF=off
```

Текущий контейнерный runtime больше не использует upstream-образ с runtime-патчем. Теперь сервис `open-webui` в [docker-compose.yaml](../../docker-compose.yaml) собирается прямо из локального форка `/home/seral/HDD/proj/open-webui`.

Из этого следуют три правила:

- все рабочие runtime-параметры по-прежнему сначала берём из `agent-navigator-pro`;
- поведение long-running панели, guard неподтверждённого запуска и legacy/debug `session RAG handoff` теперь должно жить в самом форке, а не в `entrypoint.sh` и не в monkeypatch-слое.
- нативный `Knowledge/RAG` остаётся владельцем `Open WebUI`; `session RAG handoff` включается только явно для совместимого отладочного контура.

Это означает:

- форк должен стартовать в том же рабочем режиме, что и контейнерный сервис продукта;
- если меняем что-то в форке, мы сравниваем это не с абстрактным upstream, а с нашим реальным продуктовым контейнером;
- все важные параметры запуска сначала считаются из `agent-navigator-pro`, а уже потом воспроизводятся во форке.

## 3. Что не нужно тащить в задачу

`Hugging Face` сейчас не является блокирующей частью для основного пользовательского контура.

Почему:

- продуктовый `open-webui` контейнер уже работает с `HF_HUB_OFFLINE=1`;
- основной LLM идёт во внешний `agent-api`;
- эмбеддинги идут во внешний `ums`;
- `qdrant` используется как векторная база, а не как хранилище долгих задач.

Следствие:

- для работы над `deep-job` не нужно строить решение вокруг локальных `hf`-загрузок;
- предупреждения про локальный `snapshot` сами по себе не являются блокером, если ответы `/health`, `/ready` и сам интерфейс работают;
- для текущей задачи важнее воспроизвести рабочую конфигурацию `Open WebUI`, чем чинить весь офлайн-контур `hf`.

## 5. Как запускать форк из исходников

Работаем из `conda`, отдельный `venv` не нужен.

### Установка зависимостей

```bash
cd /home/seral/HDD/proj/open-webui
npm install
python -m pip install --upgrade pip
python -m pip install -e .
```

### Сборка клиентской части

```bash
cd /home/seral/HDD/proj/open-webui
./node_modules/.bin/vite build
```

Это нужно потому, что запуск через `open-webui serve` без собранной клиентской части может уйти в режим только API.

### Локальный запуск из исходников

```bash
cd /home/seral/HDD/proj/open-webui
OPENAPI_TOOL_SERVER_TOKEN=agent-navigator-tool-server-dev-token-change-me \
OFFLINE_MODE=true \
ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS=false \
ENABLE_BASE_MODELS_CACHE=false \
FRONTEND_BUILD_DIR=/home/seral/HDD/proj/open-webui/build \
open-webui serve --host 127.0.0.1 --port 8081
```

Назначение параметров:

- `OFFLINE_MODE=true` — не тянуть внешние зависимости и не уходить в сеть;
- `ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS=false` — не ставить пакеты автоматически для инструментов и функций;
- `ENABLE_BASE_MODELS_CACHE=false` — не пытаться заранее строить каталог моделей;
- `FRONTEND_BUILD_DIR=.../build` — отдавать локально собранную клиентскую часть.
- `OPENAPI_TOOL_SERVER_TOKEN=...` — обязателен для proxy-маршрутов `deep_jobs`, если `run_native` форк не синхронизирован отдельным `TOOL_SERVER_CONNECTIONS`.

## 6. Какой запуск считать эталонным

У нас есть два полезных режима.

### Режим A. Продуктовый эталон

Это контейнерный `Open WebUI` из `agent-navigator-pro`:

```bash
cd /home/seral/HDD/proj/agent-navigator-pro
docker compose --profile legacy up -d open-webui
```

Этот режим нужен для:

- проверки текущего поведения продукта;
- сравнения с форком;
- подтверждения, что новый подход не ломает рабочий контур смешанного запуска.

### Режим B. Разработка форка

Это запуск `Open WebUI` из исходников в `/home/seral/HDD/proj/open-webui` на отдельном порту, например `8081`.

Этот режим нужен для:

- правок платформенного кода;
- локальной проверки `Chat.svelte`, компонента отображения, сериализатора и `Stop`;
- последующей сборки собственного образа.

Короткое правило:

- продукт сравниваем на контейнере;
- код меняем и проверяем во форке из исходников;
- потом собираем свой контейнерный образ уже из форка.

## 7. Как работать с двумя репозиториями

### Сначала меняем во форке `open-webui`

Если задача относится к:

- постоянной панели `deep-job`;
- компонента отображения сообщения;
- сериализации `open_webui:deep_job`;
- общему `Stop`;
- логике восстановления панели после `reload`;

то это работа во форке `open-webui`.

### Потом синхронизируем `agent-navigator-pro`

Если после изменений во форке нужно:

- поменять образ контейнера;
- обновить деплой-конфигурацию;
- обновить руководство;
- подстроить интеграционные тесты;
- поменять продуктовый `bootstrap` или тестовый контур;

то это уже работа в `agent-navigator-pro`.

Иными словами:

- форк `open-webui` — место платформенной реализации;
- `agent-navigator-pro` — место интеграции, запуска и проверки.

## 9. Что считать существующим upstream-долгом по `npm run check`

Полный `npm run check` во форке сейчас не является чистым критерием регрессии для наших изменений.

На `v0.8.12` уже есть большой хвост типовых ошибок и предупреждений в unrelated-файлах, в том числе:

- старые `.js`-файлы без строгой типизации и с большим количеством `implicit any`;
- существующие проблемы типизации `i18n` в Svelte-компонентах;
- старые ошибки в административных экранах и route-компонентах;
- уже существующий шум в `MarkdownTokens.svelte`.

Практическое правило такое:

- `pytest`, `python -m py_compile` и `git diff --check` остаются обязательными;
- полный `npm run check` используем как индикатор общего техдолга форка, а не как единственный сигнал по `deep-job`;
- если нужен точечный сигнал, фильтруем вывод `svelte-check` по затронутым файлам.

## 10. Политика bootstrap для старого deep-job пути

`bootstrap_openwebui.py` сохраняется как общий механизм импорта и синхронизации `Open WebUI`.

Но для чистой архитектуры `deep-job` он не должен тащить старые deep-job-ориентированные `Action Function`.

Нормальная политика такая:

- export bundle публикует пустой список `actionFunctions`;
- bootstrap не создаёт ни одну `Action Function`;
- если legacy actions уже существуют в `Open WebUI`, bootstrap должен их удалить;
- поддерживаемый UX ограничен нативной панелью, автообновлением и нативной кнопкой `Stop`.

Это нужно, чтобы новый panel-path не зависел от старого action-path даже косвенно.

## 12. Короткое правило на каждый день

Если возникает вопрос “где это менять?”:

- если это про платформенный код `Open WebUI` — менять во fork;
- если это про контур запуска, контейнер, токены, смешанный режим, `bootstrap` или продуктовые тесты — менять в `agent-navigator-pro`.

Если возникает вопрос “откуда брать параметры?”:

- брать из `agent-navigator-pro`, потому что именно он описывает реальный продуктовый контур.
