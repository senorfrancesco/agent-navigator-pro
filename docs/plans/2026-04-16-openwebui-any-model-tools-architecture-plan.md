# Архитектурный план: инструменты и `deep-job` для любой выбранной модели в `Open WebUI`

## 1. Контекст

Сейчас новый `deep-job`-контур в форке `Open WebUI` уже работает нативно: есть постоянная панель, автоматическое обновление, terminal result и общий `Stop`. Но для демонстрации и надёжного запуска используется модель `llm-tools-platform`, которая фактически играет роль временного шлюза к инструментальному контуру.

Это допустимо как переходный этап, но не соответствует целевой архитектуре проекта.

Целевая пользовательская модель должна быть другой:

- пользователь выбирает обычную модель из списка;
- выбранная модель остаётся пользовательским параметром диалога;
- инструменты, включая `deep-job`, доступны не через отдельную специальную модель, а через общий инструментальный слой;
- `deep-job` и обычные tool-вызовы не привязаны к одному `model id`;
- процессный UX долгой задачи не меняется в зависимости от выбранной модели: промежуточное выполнение остаётся панелью и состоянием процесса, а не разговорной репликой модели.
- пользовательский слой long-running сценария показывает общий класс `Инструмент долгого выполнения` и отдельно конкретное имя инструмента.

## 2. Проблема

Если оставить `llm-tools-platform` как единственный способ работы с инструментами, возникают архитектурные дефекты:

1. В интерфейсе появляется искусственная специальная модель, которой в целевой системе не должно быть.
2. Пользователь не может воспринимать список моделей как настоящий список доступных рабочих моделей.
3. Инструменты и `deep-job` оказываются связаны не с оркестратором, а с конкретным `model id`.
4. Acceptance и документация начинают неявно закреплять неверный контракт: “инструменты работают только у специальной модели”.
5. Дальнейшая унификация каталога моделей через `UMS` становится сложнее, потому что специальная модель маскирует реальную проблему маршрутизации.

## 3. Цель

Нужно закрепить целевую архитектуру, в которой:

- нет обязательной специальной модели для инструментов;
- `Open WebUI` показывает пользователю обычные модели;
- выбранная пользователем модель передаётся в общий инструментальный шлюз как параметр;
- один и тот же инструментальный слой умеет:
  - отдавать обычный ответ без инструментов;
  - выполнять `tool calls`;
  - запускать `deep-job`;
  - использовать выбранную модель как базовую модель генерации;
- `deep-job` остаётся частью общего tool-контракта, а не свойством отдельной модели.

## 4. Нормативное решение

### 4.1. Специальная модель не является целевой архитектурой

`llm-tools-platform` не должен закрепляться как обязательная пользовательская модель для инструментов.

Допустимо только временное существование:

- как совместимого алиаса;
- как диагностического маршрута;
- как переходного compatibility surface.

Недопустимо:

- считать его основным пользовательским способом работы с инструментами;
- строить acceptance вокруг предположения, что инструменты доступны только через него;
- проектировать `deep-job` как функцию специальной модели.

### 4.2. Каноническая архитектура

Каноническая схема должна быть такой:

1. `Open WebUI` показывает список обычных моделей.
2. Пользователь выбирает модель как часть обычного chat UX.
3. Запрос идёт в единый tool-aware gateway.
4. Gateway получает:
   - пользовательский prompt;
   - `chat_id`;
   - выбранный `model id`;
   - метаданные текущего tool-контекста.
5. Gateway решает:
   - нужен ли обычный ответ;
   - нужен ли explicit tool call;
   - нужен ли `deep-job`.
6. Если нужен inference без инструментов, gateway использует выбранную модель напрямую.
7. Если нужен инструментальный путь, gateway использует ту же выбранную модель как модель планирования или генерации, но инструменты и `deep-job` остаются общими.

### 4.3. Разделение ответственности

`Open WebUI` отвечает за:

- выбор модели пользователем;
- отображение панели `deep-job`;
- terminal result;
- общий `Stop`;
- сохранение UI-якоря `open_webui:deep_job`.

`agent-api` отвечает за:

- tool-routing;
- запуск и жизненный цикл `tool_jobs`;
- `deep-job`;
- оркестрацию между выбранной моделью и инструментами.

`UMS` отвечает за:

- канонический каталог моделей;
- публичный `OpenAI-compatible` model gateway;
- runtime-backed видимость и доступность моделей.

### 4.4. Что считается “любой моделью”

Под “любой моделью” в этом плане понимается не абсолютно каждая запись в системе, а любая пользовательская chat-модель, которая:

- публикуется в общем каталоге;
- доступна через canonical provider path;
- допускается для обычного chat-контура.

Важно:

- архитектурно инструменты должны быть доступны для всех таких моделей;
- качество tool-calling может отличаться от модели к модели;
- различие в качестве не должно превращаться в архитектурную привязку инструментов к одной специальной модели.

### 4.5. Инференс: одна активная генеративная модель

Для текущего продукта нормативным считается не набор параллельно загруженных `LLM`-профилей, а один активный генеративный runtime:

1. Пользователь выбирает модель в `Open WebUI`.
2. Эта модель становится текущей активной генеративной моделью диалога.
3. `UMS`, `agent-api`, `LangGraph`, `LangChain` и explicit tools используют именно её для генеративных шагов, если у сценария нет жёсткого запрета по возможностям модели.

Это решение принято по причинам:

- у нас ограниченные ресурсы и нет смысла держать две тяжёлые генеративные модели одновременно;
- нам нужно честно видеть, как выбранная пользователем модель работает в реальных задачах и инструментах;
- специальные `LLM`-профили для каждого графа быстро приводят к расхождению состояния между UI, `UMS` и orchestration layer.

Следствие:

- целевой контракт опирается не на множество одновременно активных `LLM`-профилей, а на одну активную пользовательскую генеративную модель;
- служебные роли остаются отдельными только для тех классов моделей, которые по смыслу не являются пользовательским чат-инференсом.

### 4.6. Служебные модели и capability-проверки

Отдельно от активной пользовательской генеративной модели разрешено конфигурировать только служебные модели:

- `embedder`
- `reranker`
- `intent classifier`
- `vision` / `OCR`, если этот слой не обслуживается основной моделью

На первом этапе это допустимо задавать через `env` и backend registry.

Нормативное правило:

- пользовательская генеративная модель динамически меняется по выбору пользователя;
- служебные модели остаются backend-owned конфигурацией;
- orchestration layer не должен молча подменять пользовательскую модель другой тяжёлой `LLM`, кроме явно оговорённого fallback-контракта.

Каждый workflow и инструмент должен описывать не «свой профиль модели», а требования к возможностям модели:

- поддержка инструментов;
- поддержка `vision`;
- допустимость для структурированного вывода;
- достаточный контекст;
- пригодность для long-running planning / execution.

Если активная модель требованиям не соответствует, backend должен:

1. либо вернуть понятный отказ/подсказку о несовместимости;
2. либо использовать явно заданный fallback, если такой fallback введён как отдельное архитектурное решение.

### 4.7. Временная конфигурация по умолчанию

До отдельного среза по расширенному model registry baseline остаётся:

- пользовательская генеративная модель по умолчанию — `Qwen2.5 Instruct 14B` / `qwen-14b-llm`;
- служебные модели задаются backend-конфигурацией;
- `Open WebUI` не становится владельцем путей к служебным моделям и не хранит их как пользовательские chat-model selection state.

### 4.8. Фактический инвентарь `backend/models`

На текущем узле уже лежит не абстрактный, а вполне конкретный baseline моделей, и дальнейший registry нужно строить именно от него, а не от общего `raw`-сканирования.

Что уже подтверждено как фактический baseline на диске и совпадает с текущим registry / `.env`:

- `backend/models/st/LaBSE`: текущий retrieval baseline `labse-embedding`.

Что уже есть в static registry, но ещё не подтверждено как локально готовый runtime на этом узле:

Что лежит на диске как реальные следующие кандидаты на регистрацию:

- `backend/models/gguf/qwen2.5-32b-q4/qwen2.5-32b-instruct-q4-merged.gguf`: первый кандидат на добавление как `qwen-32b-llm`;

- `backend/models/gguf/huggingface/download/WizardLM-30B-Uncensored.Q4_K_M.gguf.lock` и `.incomplete`-артефакты загрузки не являются готовыми моделями и не должны появляться в каталоге;
- `backend/models/onnx/labse.onnx` и `onnx`-подкаталоги внутри `sentence-transformers` не должны автоматически публиковаться как отдельные selectable entries без отдельного runtime-контракта.

Отдельно важно: в `backend/models` сейчас не найдено ни `adapter_config.json`, ни `adapter_model.safetensors`, ни `*lora*.gguf`. Это значит, что `LoRA` / `QLoRA`-поддержка остаётся архитектурным follow-up, но пока не является активным runtime-case для текущего инвентаря на узле.

## 5. Разделение реализации по репозиториям

### 5.1. Что нужно делать во форке `Open WebUI`

Форк в [/home/seral/HDD/proj/open-webui](/home/seral/HDD/proj/open-webui) отвечает только за пользовательский слой выбора и отображения:

- подготовленный список доступных пользовательских chat-моделей из backend-реестра;
- выбор активной модели пользователем;
- отображение статуса переключения модели;
- передача выбранного `model id` в backend без скрытой подмены на специальную tool-модель;
- отображение capability-ограничений, если backend сообщает, что активная модель не подходит для конкретного инструмента или сценария;
- отображение существующей панели `System Prompt` / `Advanced Params` для request-time параметров генерации;
- отображение отдельного действия `Reload` / `Apply and Reload` для параметров загрузки модели по образцу `Unsloth`.

Интеграция с `UMS` должна быть опциональным адаптером, а не обязательной зависимостью форка:

- без включённого адаптера форк стартует и работает как обычный `Open WebUI`;
- стандартные провайдеры, настройки, знания, функции, голос и базовый чат не зависят от доступности `UMS`;
- runtime-модели из папок, загрузка в память, отмена загрузки и административная регистрация доступны только при явном включении `ENABLE_AGENT_NAVIGATOR_RUNTIME_MODELS`;
- если адаптер включён, но `UMS` недоступен, деградирует только runtime-слой локальных моделей, а не весь интерфейс.

Отдельно фиксируется требование по встроенному menu / settings sidebar по образцу `Unsloth`:

- это должен быть один встроенный UI-контур настроек чата и активной модели, а не набор разрозненных экранов;
- внутри него должны жить:
  - выбор активной модели;
  - `System Prompt` с коротким inline-редактором и переходом в расширенный редактор;
  - `Advanced Params` для request-time параметров;
  - статус активной модели и процесса загрузки;
  - отображение backend-recommended defaults для выбранной модели;
  - capability-индикаторы вроде поддержки инструментов, reasoning, vision и доступного контекста, если backend их возвращает.

Поведение этого menu должно повторять полезную часть `Unsloth`, а не только визуальную форму:

- после загрузки или переподключения страницы UI повторно гидрирует effective inference-параметры из backend runtime state;
- backend defaults накладываются на UI автоматически, но пользователь может делать chat-level override;
- UI повторно гидрирует фактические runtime-лимиты активной модели, включая доступный контекст и производные ограничения `max_tokens`, а не держит эти значения как чисто локальные предположения;
- при активной загрузке модели пользователь видит progress и отдельное действие остановки загрузки;
- если backend требует `trust_remote_code`, UI должен показать это как явное подтверждаемое состояние, а не как скрытую техническую деталь;
- для request-time параметров допустимы встроенные presets, если они не ломают backend-owned defaults и capability-проверки.

Уточнение по UX:

- при обычном выборе другой модели отдельное действие `Reload` не требуется, потому что сам выбор уже означает активацию новой модели;
- отдельное `Reload` / `Apply and Reload` допустимо только для изменения loader/runtime-параметров уже выбранной модели в административном режиме.

Ключевые точки форка:

- модельный store: [/home/seral/HDD/proj/open-webui/src/lib/stores/index.ts](/home/seral/HDD/proj/open-webui/src/lib/stores/index.ts)
- агрегатор списка моделей: [/home/seral/HDD/proj/open-webui/backend/open_webui/utils/models.py](/home/seral/HDD/proj/open-webui/backend/open_webui/utils/models.py)
- текущий chat selector: [/home/seral/HDD/proj/open-webui/src/lib/components/chat/ModelSelector.svelte](/home/seral/HDD/proj/open-webui/src/lib/components/chat/ModelSelector.svelte)
- текущий workspace import contour: [/home/seral/HDD/proj/open-webui/src/lib/components/workspace/Models.svelte](/home/seral/HDD/proj/open-webui/src/lib/components/workspace/Models.svelte)

Во форке не должно жить:

- резолв локальной модели в runtime-конфигурацию;
- определение `4bit`/`trust_remote_code`/`mmproj`;
- владение активной генеративной моделью в обход `UMS`;
- хранение путей к служебным моделям как UI-owned state.
- использование `Workspace -> Models` `.json`-импорта как основного пути регистрации локальных inference-моделей.

Обычный пользователь должен выбирать модель только из подготовленного списка доступных моделей. Отдельный поток «добавить модель по пути» остаётся административной функцией и не является частью основного пользовательского UX.

Отдельно фиксируется текущий structural gap форка `Open WebUI`:

- chat selector уже умеет выбирать готовые `model_id` из списка;
- но `Workspace -> Models` contour сейчас построен вокруг `.json`-импорта и ручного ввода model-entry метаданных;
- этот contour подходит для workspace preset-объектов и локальных описаний моделей внутри самого `Open WebUI`, но не подходит как канонический путь регистрации реальных runtime-моделей из `agent-navigator-pro`.

Поэтому для нашей архитектуры административный поток должен быть другим и повторять полезную часть `Unsloth`:

- не `json`-импорт model preset-файла;
- не ручной ввод `Model ID` / `Model Name` как замена runtime-регистрации;
- а backend-owned выбор папки через `json`-браузер каталогов с allowlist;
- затем preview и нормализация найденной модели на backend;
- затем явная регистрация в registry;
- и только потом появление нового `model_id` в обычном chat selector.

То есть в нашем продукте «выбрать папку с моделью» должно означать backend flow:

1. `browse-folders`;
2. `preview-model-path`;
3. `register-model`;
4. обновление общего model catalog для chat selector.

При этом `json` в нашем случае нужен только как внутренний transport/storage формат backend-слоя:

- UI не должен просить пользователя выбирать `json`-файл модели;
- backend endpoints возвращают обычные `json`-ответы для браузера каталогов, preview и регистрации;
- persisted `json`-хранилище допустимо только как внутренний dynamic registry и служебное состояние административного контура.

Нормативное разделение здесь такое:

- отдельно можно хранить список зарегистрированных scan-folders, чтобы backend повторно знал, какие корни разрешены и какие каталоги пользователь уже добавлял;
- отдельно должен храниться dynamic registry нормализованных model entries;
- scan-folder не равен модели и не должен автоматически становиться selectable entry;
- selectable entry появляется только после backend-нормализации папки в конкретный `model_id`.

То есть если администратор добавил ещё одну папку, backend может сохранить:

- сам путь scan-folder как часть служебного административного состояния;
- одну или несколько нормализованных model entries, полученных из этой папки;
- статус готовности каждой такой записи.

Но это остаётся внутренним backend-механизмом. Пользователь видит только итоговый список готовых `model_id`, а не `json`-файлы и не сырые пути.

Отдельно фиксируется, что существующая `raw`-логика не должна оставаться скрытым альтернативным контуром. Она подлежит удалению как пользовательский и системный режим выбора моделей. После перехода остаются только:

- подготовленный список моделей из backend-реестра для обычного пользователя;
- административная регистрация модели по пути с backend-нормализацией;
- появление зарегистрированной модели в общем списке выбора после успешной регистрации.

Для `gguf-vl`-моделей backend-нормализация должна работать не по файловому списку, а по логической модели:

- основной `GGUF` с весами считается моделью;
- `mmproj` считается обязательным связанным runtime-артефактом, а не отдельной записью выбора;
- в пользовательском selector должна появляться одна vision-модель, а не две записи `model + mmproj`;
- при отсутствии или неоднозначности `mmproj` модель не должна публиковаться как готовая для обычного пользователя без явного административного решения.

Тот же принцип применяется и к другим составным наборам файлов:

- split-модели вида `00001-of-00004`, `00002-of-00004` и далее считаются одной логической моделью, а не набором selectable-файлов;
- `LoRA` / `QLoRA`-адаптер не считается самостоятельной базовой моделью, а описывается как отдельная логическая запись поверх `base_model_ref`;
- merged-экспорт адаптера, уже превращённый в обычный `GGUF`, считается обычной моделью и не требует отдельного adapter-контракта в UI.

### 5.2. Что нужно делать в `agent-navigator-pro`

`agent-navigator-pro` остаётся источником истины для inference runtime:

- model registry;
- резолв пользовательской локальной модели в backend-owned спецификацию;
- capability-флаги;
- activation / preload / stop / status;
- выбор служебных моделей;
- orchestration policy и совместимость с `LangGraph`, `LangChain` и explicit tools.

Ключевые точки:

- `UMS`: [/home/seral/HDD/proj/agent-navigator-pro/backend/services/model_manager/unified_model_server.py](/home/seral/HDD/proj/agent-navigator-pro/backend/services/model_manager/unified_model_server.py)
- текущая конфигурация моделей: [/home/seral/HDD/proj/agent-navigator-pro/backend/services/model_manager/models_config.py](/home/seral/HDD/proj/agent-navigator-pro/backend/services/model_manager/models_config.py)
- orchestration entrypoint: [/home/seral/HDD/proj/agent-navigator-pro/backend/orchestrator/agent_api.py](/home/seral/HDD/proj/agent-navigator-pro/backend/orchestrator/agent_api.py)

Именно здесь нужно внедрять заимствования из `Unsloth`:

- backend-сканирование пользовательских папок;
- backend `json`-браузер каталогов по allowlist вместо прямого `Workspace -> Models` `.json`-импорта;
- единый `ModelConfig`/`ModelDescriptor` слой;
- автоподстановку параметров загрузки;
- inference defaults по модели/семейству;
- capability-матрицу;
- связь `selected model -> active_model_id -> orchestration`;
- явную backend-регистрацию модели по указанному пути, после которой модель попадает в общий список выбора.

Отдельно требуется аккуратный contract для `registry`:

- операторский статический реестр остаётся в `backend/config/models.yaml`;
- административные добавления по пути попадают в отдельный dynamic registry `UMS`;
- при наличии folder-browser рядом может существовать и отдельное persisted-хранилище scan-folders, но оно не подменяет dynamic registry;
- на чтении UI и orchestration должны видеть единый нормализованный каталог, собранный из static + dynamic частей;
- обе части registry обязаны оперировать не сырыми файлами, а логическими model entries со статусами готовности `ready` / `incomplete` / `ambiguous` / `unsupported`.

Минимальная структура нормализованной model entry должна включать:

- `model_id`;
- `display_name`;
- `kind`;
- `runtime_type`;
- `source`;
- `capabilities`;
- `generation_defaults`;
- `load_defaults`.

Для составных случаев в `source` требуется хранить не сырые пути из selector, а нормализованные поля:

- для `gguf-vl`: `gguf_path` и `mmproj_path`;
- для split-`GGUF`: шаблон набора и полный список `shards`;
- для адаптера: `adapter_path`, `adapter_format`, `base_model_ref`.

Отдельное правило для адаптеров:

- если runtime `llama.cpp` используется как backend, адаптер считается готовым к публикации только когда он доступен в `GGUF`-формате;
- каталог `PEFT` вида `adapter_config.json` + `adapter_model.safetensors` не должен считаться готовой `llama.cpp`-моделью без отдельной backend-конвертации или другого runtime;
- для `llama.cpp` запуск адаптера должен опираться на штатные флаги `--lora` / `--lora-scaled`, а не на пользовательский выбор сырых adapter-файлов в UI;
- если адаптер загружается в `llama-server`, backend может использовать и серверный путь с предзагрузкой адаптеров и последующим управлением через `/lora-adapters`, но этот механизм остаётся backend-owned и не раскрывается как отдельный пользовательский selector.

## 6. Целевой контракт

### 6.1. Контракт выбора модели

`Open WebUI` не должен переключаться на отдельную специальную tool-модель ради запуска инструментов.

Вместо этого выбранный пользователем `model id` должен передаваться как часть канонического запроса в backend.

### 6.2. Контракт gateway

Gateway должен уметь принять один запрос и на его основе:

- определить выбранную модель;
- сохранить её как базовую модель текущего сообщения;
- выполнить обычный ответ или инструментальный сценарий;
- при необходимости запустить `deep-job` без подмены пользовательского выбора на отдельную специальную модель.

### 6.3. Контракт `deep-job`

`deep-job` остаётся общей сущностью инструментального слоя:

- хранится в `tool_jobs`;
- отображается в `Open WebUI` через panel-path;
- не зависит от конкретной специальной модели;
- может запускаться из любого диалога, где выбранная модель идёт через общий tool-aware path.

При этом пользовательский контракт `deep-job` должен оставаться одинаковым для любой выбранной модели:

- до terminal state отображается только процесс выполнения и панель `deep-job`;
- панель показывает общий класс `Инструмент долгого выполнения` и отдельно имя конкретного long-running инструмента;
- модель не должна писать промежуточные обещания в будущем времени;
- содержательный итог публикуется только после завершения;
- пока активен `deep-job`, обычный новый turn не должен исполняться параллельно вне очереди.

### 6.4. Контракт нормализованного execution-слоя

Для long-running инструментов пользовательский UI не должен зависеть напрямую от внутреннего runtime-фреймворка.

Нормой считается следующая схема:

1. Источником истины остаётся `tool_jobs`.
2. Поверх `tool_jobs` существует единый execution-контракт long-running инструмента.
3. Этот контракт отдаёт стабильные поля:
   - `state`
   - `current_stage`
   - `status_text`
   - `status_history`
   - `progress`
   - `tool_label`
4. `Open WebUI` рендерит только этот контракт.

Если конкретный инструмент реализован на `LangGraph` или `LangChain`, их события считаются только внутренним источником данных для адаптера.

Недопустимо:

- привязывать пользовательскую панель к сырым именам узлов графа;
- строить UI как прямой просмотр callback-событий framework;
- допускать, чтобы формат `LangGraph` или `LangChain` становился публичным UI-контрактом для long-running инструментов.

## 7. Этапы внедрения

### Этап 1. Зафиксировать правильный контракт

Нужно явно закрепить в документации и acceptance:

- специальная модель не является целевым решением;
- целевое решение — общий tool-aware gateway для обычных моделей.

### Этап 2. Ввести inference split: одна активная `LLM` + служебные модели

Нужно отдельно закрепить:

- одна активная пользовательская генеративная модель;
- отдельная backend-конфигурация служебных моделей;
- capability-проверка перед запуском инструментов и graph/workflow path;
- baseline по умолчанию остаётся `qwen-14b-llm`, пока не появится новый подтверждённый default.

### Этап 3. Развести временный и целевой маршруты

Нужно отделить:

- временный compatibility path через `llm-tools-platform`;
- целевой path через выбранную модель + единый инструментальный шлюз.

Пока gateway не готов полностью, compatibility alias может существовать, но не должен маскировать целевую архитектуру.

### Этап 4. Привести `Open WebUI` к model-preserving поведению

Во форке `Open WebUI` нужно обеспечить, чтобы:

- выбор модели пользователем сохранялся;
- новый panel-path `deep-job` не зависел от специальной модели;
- интерфейс и acceptance не предполагали ручного переключения на особую tool-модель;
- процессный UX `deep-job` был одинаковым независимо от выбранной модели.

### Этап 5. Довести backend gateway и model runtime

На стороне backend нужно сделать так, чтобы выбранная модель:

- доходила до tool-aware orchestration слоя;
- использовалась как базовая модель генерации;
- не подменялась специальной моделью в скрытом режиме без явного архитектурного решения.
- могла динамически активироваться в `UMS`, если пользователь сменил модель;
- проверялась по capability-флагам до запуска инструмента или workflow;
- не ломала служебные пути `embedder` / `classifier` / `reranker`.

### Этап 6. Убрать специальную модель из канонического UX

После завершения gateway-migration:

- `llm-tools-platform` перестаёт быть required user-facing моделью;
- acceptance больше не опирается на неё;
- демонстрации и smoke-проверки идут через обычный выбор модели.

### Этап 7. Согласовать model gateway и процессный UX

После внедрения общего gateway нужно отдельно подтвердить, что:

- выбранная модель не меняет пользовательский контракт долгой задачи;
- промежуточный `deep-job` не превращается в обычный “дописываемый” ответ модели;
- блокировка ввода или постановка в очередь работают одинаково для всех поддерживаемых моделей.

## 8. Ограничения

Этот план:

- не заменяет текущий `deep-job`-план во форке `Open WebUI`;
- не отменяет существующий план унифицированного model catalog / gateway;
- не требует немедленного удаления compatibility alias;
- не утверждает, что все модели одинаково качественно вызывают инструменты.

Этот план утверждает только архитектурную норму:

- инструменты и `deep-job` принадлежат общему инструментальному слою;
- они не должны быть навсегда привязаны к отдельной специальной модели.

## 9. Definition of Done

Задача считается архитектурно закрытой, когда одновременно выполняются условия:

- в документации явно зафиксировано, что специальная модель не является целевым контрактом;
- `Open WebUI` может запускать инструменты и `deep-job`, сохраняя пользовательский выбор модели;
- у продукта есть отдельный inference-контракт: одна активная пользовательская генеративная модель + backend-owned служебные модели;
- `UMS` и orchestration используют один и тот же `active_model_id` для генеративных шагов;
- acceptance не опирается на специальную модель как обязательный способ работы с инструментами;
- `llm-tools-platform` остаётся только совместимым переходным маршрутом или полностью исчезает из пользовательского контура;
- `deep-job` подтверждён как часть общего tool-aware gateway, а не как функция одного `model id`;
- процессный UX `deep-job` не меняется при переключении между поддерживаемыми моделями.
- long-running панель показывает единый класс выполнения и отдельное имя инструмента, не завися от конкретного runtime-фреймворка;
- состояния и этапы панели приходят из нормализованного execution-контракта поверх `tool_jobs`, а не напрямую из `LangGraph` или `LangChain`.
- служебные модели (`embedder`, `classifier`, `reranker`, `vision`) остаются backend-owned и не смешиваются с пользовательским выбором chat-модели.
