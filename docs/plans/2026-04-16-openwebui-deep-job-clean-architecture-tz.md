## 2. Текущая реализация и проблема

Сейчас контур долгих задач уже работает технически:

- запуск инструмента возвращает `accepted` и `job_id`;
- состояние хранится в `tool_jobs`;
- есть `/tool-jobs/{id}`, `/result`, `/cancel`, `/delivery`;
- исторический `Open WebUI`-контур умел через импортированные `Action Function` запускать `deep-job`, обновлять состояние и показывать terminal result; этот путь теперь снят с поддержки.

Но текущая пользовательская модель остаётся архитектурно слабой:

1. Основное отображение состояния завязано на `status-bubble`, `refresh` и временный DOM-патч.
2. Состояние выглядит как надстройка, а не как полноценная часть assistant-message.
3. `bubble` ведёт себя как временный слой и воспринимается как костыль.
4. Кнопки `Обновить deep-job` и `Отменить deep-job` являются отдельной механикой вместо нормального общего `Stop`.
5. Поведение долгой задачи живёт во временном слое патча и импортированных функциях, а не в штатной архитектуре `Open WebUI`.
6. Уже есть риск расхождения между кодом в репозитории и тем, что фактически импортировано в `Open WebUI`.

Нужно заменить эту модель на чистую архитектуру, в которой долгий `deep-job` выглядит как постоянная панель внутри assistant-message и не требует ручного `refresh`.

При этом пользовательский слой должен описывать не абстрактный `deep-job`, а класс выполнения:

- общий класс панели: `Инструмент долгого выполнения`;
- конкретный сценарий внутри панели: отдельное человекочитаемое имя инструмента, например `Глубокий анализ оборудования` или `Глубокий анализ документа`;
- состояния и этапы панели должны оставаться едиными для всех long-running инструментов, а не зависеть от одного частного deep-route.

## 3. Цель задачи

Нужно реализовать в `Open WebUI` чистую архитектуру отображения и управления долгими инструментальными задачами, оставаясь на платформе `Open WebUI` и не добавляя новое каноническое хранилище поверх уже существующего `tool_jobs`.

Итоговое поведение должно быть таким:

- `deep-job` отображается как постоянная панель внутри assistant-message;
- панель показывает общий класс `Инструмент долгого выполнения` и отдельно конкретное имя инструмента;
- панель не исчезает после следующих сообщений и переживает `reload`;
- обновление состояния происходит автоматически;
- главный `Stop` работает как реальная отмена активной долгой задачи;
- состояние долгой задачи берётся из существующего `tool_jobs`, а не из `bubble`, не из `qdrant` и не из отдельного нового `deep_jobs`;
- исторический `legacy_patch` не должен возвращаться в рабочий runtime после переноса поведения во форк.

Тип задачи: архитектурный рефакторинг, переработка пользовательского контура долгих инструментов и подготовка поддерживаемого форка `Open WebUI`.

## 4. Варианты реализации

### Вариант A. Оставить текущий `bubble`-контур и только улучшить автообновление

Суть:

- оставить `tool_job_refresh_action`;
- оставить `status-bubble`;
- оставить `legacy_patch`;
- улучшить `autopoll`, скрытие кнопок и terminal result.

Плюсы:

- самый дешёвый по внедрению;
- минимальные изменения в `Open WebUI`.

Минусы:

- не даёт чистой архитектуры;
- сохраняет костыльную пользовательскую модель;
- оставляет зависимость от временного патча и ручного action-path;
- главный `Stop` по-прежнему будет неестественно связан с отдельной механикой `deep-job`.

Статус: допустим только как временный обход, не как целевая архитектура.

### Вариант B. Новое отдельное хранилище `deep_jobs` внутри форка `Open WebUI`

Суть:

- завести отдельную таблицу `deep_jobs` в `Open WebUI`;
- синхронизировать её с существующим `tool_jobs`;
- рендерить панель по данным этого нового хранилища.

Плюсы:

- внутри форка `Open WebUI` всё выглядит локально и изолированно;
- удобно проектировать отдельный API под панель.

Минусы:

- дублирует уже существующее состояние долгих задач;
- создаёт второй канонический источник истины;
- повышает вероятность рассинхронизации между `tool_jobs` и `deep_jobs`;
- усложняет поддержку и отладку.

Статус: не рекомендуется.

### Вариант C. Тонкий форк `Open WebUI` + повторное использование `tool_jobs` как единственного хранилища

Суть:

- каноническое состояние долгой задачи остаётся в существующем `tool_jobs` проекта;
- форк `Open WebUI` получает только полноценный пользовательский слой для `deep-job`;
- в assistant-message хранится лёгкий якорь с `job_id`;
- `Open WebUI` делает серверный прокси-запрос к существующим маршрутам `/tool-jobs` в `agent-api`;
- интерфейс показывает постоянную панель, а не отдельный `bubble`.

Плюсы:

- чистая архитектура без дублирования хранилищ;
- используется уже работающий серверный контур жизненного цикла;
- минимизируется объём новой предметной логики;
- проще поддерживать форк и обновлять его на новых upstream tag.

Минусы:

- требует поддерживаемого форка `Open WebUI`;
- требует переработки клиентского и серверного слоя самого `Open WebUI`.

Статус: **рекомендуемый целевой вариант**.

## 5. Требования к функционалу

### 5.1. Канонический источник истины

Каноническое состояние долгой задачи должно жить в существующем `tool_jobs` серверного контура проекта.

Запрещено:

- заводить второе равноправное хранилище для той же сущности;
- использовать `qdrant` для состояния долгой задачи;
- считать `message.output`, `statusHistory`, DOM, `bubble` или клиентское хранилище состояния источником истины.

### 5.2. Привязка к assistant-message

Каждый `deep-job` должен быть привязан к одному assistant-message через `job_id`.

В `message.output` должен храниться лёгкий placeholder item, например:

```json
{
  "type": "open_webui:deep_job",
  "job_id": "job_123",
  "title": "Глубокий анализ",
  "summary": "Задача принята",
  "state": "queued"
}
```

Назначение placeholder:

- дать панели стабильную привязку к сообщению;
- восстановить панель после `reload`;
- не хранить в сообщении полное состояние задачи.

### 5.3. Автоматическое обновление без `refresh/update`

Пользователь не должен нажимать `refresh deep_job` или `update deep_job`.

В `v1` нужно:

- убрать из канонического пользовательского контура ручные action-кнопки `refresh/update`;
- выполнять автоматическое обновление состояния через `polling`;
- останавливать `polling` в терминальном состоянии;
- выполнять быстрый повторный запрос на `focus/reload`.

### 5.4. Постоянная панель вместо `bubble`

`deep-job` должен отображаться как отдельная постоянная панель внутри assistant-message, а не как временный `status-bubble`.

Панель должна показывать:

- общий класс `Инструмент долгого выполнения`;
- отдельное имя конкретного инструмента;
- состояние: `queued`, `running`, `completed`, `failed`, `cancelled`;
- краткую сводку;
- фазу выполнения;
- прогресс, если он есть;
- историю шагов;
- отдельный блок ошибки для `failed`;
- terminal summary или ссылку на terminal result для завершённой задачи.
- если deep-route сформировал отчёт, итоговое terminal сообщение должно содержать пользовательскую ссылку `Скачать отчёт`, а скачивание должно отдавать `pdf` через backend/proxy-маршрут.

Панель не должна притворяться прямым отладочным отображением фреймворка графов. Пользователь видит общий класс long-running выполнения и конкретный инструмент, а не внутреннее имя runtime.

### 5.5. Нормализованный контракт состояний и этапов

`Open WebUI` не должен опираться напрямую на сырые события `LangGraph` или `LangChain`.

Канонический пользовательский контракт должен строиться только на нормализованном execution-слое поверх `tool_jobs`.

Этот слой обязан выдавать устойчивые поля:

- `state` как общий жизненный цикл задачи;
- `current_stage` как текущий этап выполнения;
- `status_text` как краткую сводку текущего шага;
- `status_history` как историю этапов;
- `progress` как необязательные числовые или фазовые подсказки;
- `tool_label` как отображаемое имя конкретного long-running инструмента.

Если конкретный workflow использует `LangGraph` или `LangChain`, их события должны сначала переводиться в этот нормализованный execution-контракт, и только затем попадать в UI.

Недопустимо:

- привязывать рендер панели к сырым именам узлов `LangGraph`;
- делать `Open WebUI` зависимым от формата callback-событий `LangChain`;
- строить пользовательскую панель как прямой дамп runtime graph state.

### 5.6. Процессный пользовательский контракт

Пока `deep-job` активен, интерфейс должен показывать именно процесс выполнения, а не “реплику модели, которая потом допишется”.

Это означает:

- промежуточное состояние отображается через панель `deep-job` и связанные статусные обновления;
- модель не должна писать разговорные фразы в будущем времени вроде:
  - `После завершения анализа я предоставлю...`
  - `Пожалуйста, дождитесь завершения...`
  - `Я сейчас проанализирую и затем вернусь с итогом`
- допустимы только процессные формулировки в настоящем времени, например:
  - `Глубокий анализ выполняется`
  - `Идёт извлечение требований`
  - `Идёт формирование итогового ответа`
- содержательный пользовательский ответ публикуется только один раз, отдельным terminal `assistant-message` после завершения задачи;
- до terminal state чат не должен создавать впечатление, будто модель “просто продолжит дописывать это же сообщение”.

### 5.7. Режим ввода во время активного `deep-job`

Пока в чате есть активный `deep-job`, обычный ввод не должен вести себя как свободный новый диалоговый ход.

Требования:

- основной управляющий элемент рядом с полем ввода должен оставаться в режиме `Stop`;
- пользователь не должен получать впечатление, что можно параллельно вести обычный новый turn с той же моделью;
- если в проекте уже есть очередь пользовательских запросов, новые сообщения должны идти в эту очередь, а не немедленно исполняться как обычный chat turn;
- если очередь не используется для конкретного сценария, ввод должен быть явно заблокирован до terminal state активного `deep-job`.

### 5.7. Главный `Stop`

Главный `Stop` рядом с полем ввода должен:

- учитывать наличие активного `deep-job` в текущем чате;
- если активен `deep-job`, вызывать реальную отмену через текущий `cancel`-path;
- не создавать новый assistant-message при остановке;
- не переводить интерфейс в отдельную ветку временных статусных сообщений.

Допускается производная подпись `Остановка…`, если отмена уже запрошена, но каноническая машина состояний должна оставаться:

- `queued`
- `running`
- `completed`
- `failed`
- `cancelled`

### 5.8. Ограничение `v1`

В одном чате допускается только один активный `deep-job`.

Если в чате уже есть активная долгая задача, запуск новой должен:

- либо блокироваться;
- либо явно отклоняться с понятным сообщением.

Параллельные активные `deep-job` в одном чате в `v1` не поддерживаются.

### 5.9. История модели для follow-up

`open_webui:deep_job` должен оставаться сущностью только для интерфейса и не должен попадать в reconstructed prompt history как обычный текст сообщения.

Нельзя:

- отправлять в follow-up prompt сырую историю шагов;
- отправлять в модель полный журнал статусов;
- использовать панель `deep-job` как обычный текстовый контент диалога.

### 5.10. Кросс-режимное скачивание отчёта

Скачивание отчёта должно одинаково корректно работать:

- в `run_native`-режиме форка `Open WebUI`;
- в контейнерном `Open WebUI` при mixed-runtime контуре.

Требования:

- UI не должен получать прямой путь файловой системы;
- итоговое terminal сообщение должно содержать `Скачать отчёт`, если итог задачи включает report artifact;
- `Open WebUI` должен скачивать отчёт через собственный backend/proxy-маршрут;
- tool-server должен отдавать реальный `pdf` по имени артефакта;
- acceptance не считается завершённым без отдельной проверки скачивания `pdf` в обоих режимах.

## 6. Ограничения и запреты

Нельзя:

- использовать `qdrant` как хранилище состояния долгих задач;
- вводить новое каноническое хранилище `deep_jobs`, если это дублирует `tool_jobs`;
- оставлять `refresh/update` как обязательную поверхность управления;
- создавать новый assistant-message на каждый sync;
- держать основную логику в `legacy_patch`;
- давать браузеру прямой доступ к приватному `OPENAPI_TOOL_SERVER_TOKEN`;
- превращать `reasoning` или `<think>` в основной транспорт состояния задачи;
- вводить новые пользовательские состояния кроме `queued/running/completed/failed/cancelled`.

## 7. Требования к архитектуре и коду

### 7.1. Общий принцип

Чистый архитектурный вариант должен быть реализован как тонкий поддерживаемый форк `Open WebUI` поверх pinned upstream tag.

Роли слоёв:

- `agent-api` и текущий серверный слой проекта:
  - владеют жизненным циклом долгой задачи;
  - хранят `tool_jobs`;
  - отдают `/tool-jobs/{id}`, `/result`, `/cancel`, `/delivery`.
- форк `Open WebUI`:
  - владеет пользовательским отображением;
  - владеет интеграцией общего `Stop`;
  - делает серверный прокси-запрос к `agent-api`;
  - хранит в сообщении только лёгкий placeholder с `job_id`;
  - удерживает чат в режиме выполнения, пока `deep-job` не завершён.

### 7.2. Серверная часть форка `Open WebUI`

В репозитории форка `Open WebUI` нужно реализовать серверный прокси-слой, а не новое хранилище.

Новые или изменяемые точки:

- `backend/open_webui/routers/deep_jobs.py`
- `backend/open_webui/services/deep_jobs.py`
- `backend/open_webui/main.py`

Нужные маршруты API:

- `GET /api/v1/deep-jobs/{job_id}`
- `POST /api/v1/deep-jobs/{job_id}/cancel`
- `GET /api/v1/chats/{chat_id}/deep-jobs/active`

Требования к ним:

- они не хранят вторичную доменную копию состояния;
- они проксируют и нормализуют данные из существующего `agent-api`;
- они используют серверные секреты и не раскрывают браузеру внутренний токен tool-server;
- они умеют восстанавливать активный `job_id` для чата по chat history и placeholder item.

### 7.3. Клиентская часть форка `Open WebUI`

В репозитории форка `Open WebUI` нужны:

- `src/lib/apis/deep_jobs.ts`
- `src/lib/stores/deepJobs.ts`
- `src/lib/components/chat/Messages/DeepJobDisplay.svelte`
- правка `src/lib/components/chat/Messages/Markdown/MarkdownTokens.svelte`
- правка `src/lib/components/chat/Chat.svelte`

Требования:

- отдельный компонент отображения для `deep_job`, а не generic `Collapsible`;
- `deepJobBusy` должен участвовать в логике `Stop/Send`;
- `polling` должен жить в хранилище состояния и останавливаться в терминальном состоянии;
- состояние панели должно восстанавливаться после `reload` из `job_id` и snapshot серверного слоя;
- `refresh/update` кнопки не должны быть частью `v1`.

### 7.4. Сериализация placeholder item

В репозитории форка `Open WebUI` серверный сериализатор должен поддерживать `open_webui:deep_job` как отдельный output item.

Минимально допустимый результат сериализации — placeholder, достаточный для начальной инициализации интерфейса:

- `job_id`
- `state`
- `summary`
- `title`

Нельзя встраивать в HTML большой журнал шагов или raw payload.

### 7.5. Интеграция с текущим проектом

В текущем репозитории `agent-navigator-pro` должно остаться следующее:

- `tool_jobs` как источник истины;
- `/delivery` как механизм фиксации `result_message_id`;
- `scripts/bootstrap_openwebui.py` — только для настройки соединения, prompts и конфигурации `Open WebUI`, но не как основная бизнес-логика `deep-job`;
- `tests/e2e/openwebui/deep-job.spec.ts` — как интеграционный контур проверки работы форка с серверным слоем проекта.

После перехода на форк:

- контейнерный runtime `Open WebUI` должен собираться из локального форка без `deploy/openwebui_legacy_patch`;
- bootstrap должен только синхронизировать `Open WebUI` и удалять уже установленные legacy `Action Function`;
- поддерживаемый пользовательский путь должен оставаться только native panel-path внутри форка.

## 8. Формат результата

### 8.1. Что нужно создать или изменить в репозитории форка `Open WebUI`

Создать:

- `backend/open_webui/routers/deep_jobs.py`

- `src/lib/apis/deep_jobs.ts`
- `src/lib/stores/deepJobs.ts`

- `src/lib/components/chat/Chat.svelte`
- связанные места, где сейчас используются `status-bubble` и action-refresh path для `deep_job`

### 8.2. Что нужно создать или изменить в текущем репозитории `agent-navigator-pro`

Создать или обновить:

- деплой-конфигурацию с указанием нового образа форка;
- интеграционные `Playwright`-проверки под новый интерфейс с постоянной панелью;
- при необходимости bootstrap-логику, если в `Open WebUI` остаются импортируемые артефакты, не встроенные во форк.

### 8.3. Что является готовым результатом

Готовый результат — это не просто код, а следующий комплект результата:

1. Собранный форк `Open WebUI` с постоянной панелью `deep-job`.
2. Контейнерный образ форка с pinned upstream base tag.
3. Обновлённый контур смешанного запуска, где этот образ используется вместо исходного `Open WebUI`.
4. Интеграционные тесты, подтверждающие работу нового интерфейса поверх текущего серверного слоя проекта.

## 9. Тестирование и критерии приёмки

### 9.1. Серверные и контрактные проверки

Нужно покрыть:

- получение snapshot по `job_id`;
- получение active `deep-job` по `chat_id`;
- идемпотентную отмену;
- корректную работу `queued -> running -> completed`;
- корректную работу `running -> cancelled`;
- недопустимость нетерминальных обновлений после терминального состояния;
- корректное восстановление `job_id` панели после `reload`.

### 9.2. Frontend и пользовательские проверки

Нужно проверить:

- панель появляется внутри assistant-message;
- панель не исчезает после следующих пользовательских сообщений;
- при `reload` панель восстанавливается;
- пока активен `deep-job`, главная кнопка показывает `Stop`;
- пока активен `deep-job`, чат показывает процесс выполнения, а не разговорную реплику модели в будущем времени;
- пока активен `deep-job`, обычный новый turn не исполняется параллельно вне очереди;
- `Stop` переводит задачу в режим остановки и затем в `Cancelled`;
- новые `refresh/update` кнопки отсутствуют;
- terminal result не создаёт отдельную ветку временных `bubble`.
- если deep-route сформировал отчёт, итоговое сообщение показывает `Скачать отчёт`;
- в `run_native`-режиме ссылка `Скачать отчёт` скачивает корректный `pdf`;
- в контейнерном mixed-runtime режиме ссылка `Скачать отчёт` тоже скачивает корректный `pdf`;
- скачивание идёт через backend/proxy-маршрут, а не через прямой filesystem path.

### 9.3. Интеграционные проверки в текущем проекте

Обязательно сохранить и обновить `Playwright`-контур так, чтобы он проверял:

- контур смешанного запуска с контейнерным `Open WebUI`;
- запуск `deep-job` из реального чата;
- появление постоянной панели;
- реальную запись `result_message_id` через `/delivery`;
- `reload` во время выполнения;
- `Stop` и терминальную отмену;
- отсутствие дублирования terminal result.

### 9.4. Ручной сценарий приёмки

1. Открыть чат в `Open WebUI`.
2. Запустить `deep-job`.
3. Убедиться, что появилась постоянная панель внутри assistant-message.
4. Отправить следующий пользовательский запрос.
5. Убедиться, что предыдущая панель осталась в истории.
6. Во время выполнения нажать главный `Stop`.
7. Убедиться, что:
   - не создан новый assistant-message;
   - задача реально отменяется;
   - панель меняет состояние на terminal cancelled;
   - чат возвращается в idle state только после реального завершения отмены.
8. Во время выполнения убедиться, что интерфейс показывает процесс выполнения, а не сообщение вида `после завершения я предоставлю итог`.
9. Попробовать отправить новый обычный запрос и убедиться, что он либо блокируется, либо уходит в очередь, а не исполняется как параллельный turn.
10. Перезагрузить страницу в середине выполнения и убедиться, что панель восстанавливается.

### 9.5. Критерии приёмки

Задача считается выполненной, если одновременно соблюдены все условия:

- `deep-job` больше не зависит от `refresh/update` action path;
- пользователь видит постоянную панель, а не временный `bubble`;
- панель переживает следующие сообщения и `reload`;
- единственное каноническое хранилище долгой задачи — существующий `tool_jobs`;
- `qdrant` не используется для состояния долгой задачи;
- главный `Stop` реально останавливает активный `deep-job`;
- до terminal state интерфейс показывает процесс выполнения, а не разговорное обещание будущего ответа;
- во время активного `deep-job` обычный новый turn не исполняется параллельно вне очереди;
- если deep-route сформировал отчёт, итоговое сообщение даёт `Скачать отчёт`, а скачивание `pdf` подтверждено и в `run_native`, и в контейнерном mixed-runtime режиме;
- решение поставляется как поддерживаемый форк `Open WebUI`, а не как разовый временный патч.

## 10. Релиз, контейнер и поддержка форка

Форк должен поддерживаться как тонкий слой поверх pinned upstream tag.

Требования:

- не использовать плавающие `latest` или `main` в production;
- фиксировать конкретный upstream release tag;
- держать собственный набор изменений маленьким и изолированным;
- собирать собственный контейнерный образ;
- версионировать образ по схеме вида `registry/open-webui:<upstream-tag>-deepjob.1`.

Процесс обновления:

1. Получить новый upstream tag `Open WebUI`.
2. Создать ветку обновления от этого tag.
3. Перенести свой diff через `rebase` или `cherry-pick`.
4. Прогнать smoke и интеграционные проверки.
5. Собрать новый образ.
6. Проверить стенд `staging`.
7. Только после этого выкатывать в `production`.

Обязательные эксплуатационные требования:

- постоянный `WEBUI_SECRET_KEY`;
- отдельные volume для `staging` и `production`;
- контролируемые миграции;
- обязательный smoke после обновления образа.

## 11. Особые указания для Codex

1. Реализацию проектировать вокруг варианта C, а не вокруг улучшений `bubble`.
2. Не вводить новое каноническое хранилище `deep_jobs`, если оно дублирует `tool_jobs`.
3. Не использовать `qdrant` вне его роли хранилища для поиска по векторам и retrieval.
4. Не возвращать `legacy_patch` в роль рабочего механизма долгой задачи.
5. Если в текущем репозитории нет исходников `Open WebUI`, трактовать эту задачу как отдельный поток работ для форка `Open WebUI` плюс интеграционные изменения в `agent-navigator-pro`.
6. При реализации во форке сначала стабилизировать серверный прокси-слой к `tool_jobs`, потом панель интерфейса, потом интеграцию общего `Stop`, потом удаление старого action-path.
7. Все временные переходные решения отдельно пометить как `temporary compatibility layer`, чтобы они не стали новой постоянной архитектурой.

## 12. Что не входит в задачу

В эту задачу не входят:

- перенос состояния долгих задач в `qdrant`;
- поддержка нескольких одновременных активных `deep-job` в одном чате;
- перенос старых `bubble`-историй в новый формат;
- новый отдельный протокол поверх `WebSocket` только ради `deep-job`;
- полный перепроект всего `Open WebUI` вне области долгих задач.

## 13. Короткая рекомендация по внедрению

Рекомендуется выполнять работу в четыре фазы:

1. Форк `Open WebUI` и серверный прокси-слой к текущим `tool_jobs`.
2. Постоянная панель и клиентское хранилище состояния внутри форка.
3. Интеграция общего `Stop` и удаление `refresh/update` из канонического пользовательского контура.
4. Сборка собственного контейнерного образа, проверки контура смешанного запуска, стенд `staging` и выкатка в `production`.

Это и есть целевой чистый архитектурный вариант для проекта: остаться на `Open WebUI`, не множить хранилища, не трогать роль `qdrant`, и перевести долгие задачи из временного слоя патча в поддерживаемый полноценный слой платформы.
