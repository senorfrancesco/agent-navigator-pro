## 1. Назначение документа

Этот документ фиксирует целевой архитектурный вариант для сценария:

- пользователь загружает документ через `Open WebUI`;
- документ не становится самостоятельным каноническим источником состояния внутри `Open WebUI`;
- серверная часть регистрирует документ, создаёт стабильные ссылки на него и запускает подготовку корпуса;
- поиск для обычного чата по документу и для последующих вопросов по документу опирается на `Qdrant`;
- решение должно работать на слабых и простых машинах, а не только на средних и сильных серверах.

Документ не является планом внедрения.
Его задача — зафиксировать целевую модель владения данными, жизненный цикл документа и ограничения низкоресурсного профиля, чтобы следующий план внедрения не спорил сам с собой.

---

## 2. Проблема, которую нужно решить

Сейчас в migration-материалах уже закреплены правильные базовые принципы:

- `Open WebUI` является основной пользовательской оболочкой;
- `Qdrant` рассматривается как каноническое векторное хранилище;
- разбор и `OCR` не должны жить только внутри интерфейса;
- серверная часть должна владеть `document_id`, `version_id` и состоянием инструментов и заданий.

Но в текущем наборе планов остаётся напряжение между двумя моделями:

### Модель A

- база знаний хранится в `Qdrant`;
- документы сеанса живут отдельно как локальное наложение сеанса;
- объединение происходит в серверном слое правил.

### Модель B

- пользовательская загрузка через `Open WebUI` должна быстрее становиться доступной для последующих вопросов;
- желательно не держать второй независимый контур поиска отдельно от `Qdrant`;
- обычный чат по документу и вопросы по документу в рамках сеанса должны опираться на один канонический источник поиска.

На слабых машинах проблема усиливается:

- нельзя бездумно тащить тяжёлый разбор на каждую загрузку;
- нельзя делать обязательным тяжёлый `reranker`;
- нельзя копить несколько параллельных индексов для одного и того же корпуса;
- нельзя проектировать решение так, будто всегда доступны сильный GPU, тяжёлые эмбеддеры и много фоновых сервисов.

---

## 3. Нормативное решение

### 3.1 Главная архитектурная идея

Нужно перейти к модели:

- `Open WebUI` остаётся входной точкой пользовательского взаимодействия для загрузки, чата, истории и выбора режима;
- серверная часть остаётся единственным владельцем идентичности документа;
- `Qdrant` становится единым поисковым слоем не только для постоянной базы знаний, но и для короткоживущих областей сеанса;
- при этом `knowledge` и `session` различаются не отдельными реализациями поиска, а разным жизненным циклом и фильтрами полезной нагрузки.

Иными словами:

- **одно векторное хранилище**
- **разные области и жизненный цикл**
- **один серверный слой правил**

### 3.2 Что именно считается каноническим

- вложение в `Open WebUI` — только входной пользовательский слой.
- каноническая идентичность файла — у серверной части.
- `document_ref` и состояние поиска — у серверной части.
- `Qdrant` — каноническое хранилище поиска для:
  - постоянной базы знаний;
  - короткоживущих областей документов сеанса.
- правила объединения, видимости, дедупликации, повторного ранжирования и областей поиска — у серверной части.

### 3.3 Что этот документ сознательно меняет относительно более раннего `V1`

Ранние планы допускали `V1`, где наложение сеанса живёт вне `Qdrant`.
Этот документ предлагает уточнённый целевой вариант:

- для целевого производственного направления и для ускорения пути последующих вопросов документы сеанса тоже должны уметь попадать в `Qdrant`;
- но не как постоянная база знаний;
- а как короткоживущая область с отдельными фильтрами, `TTL` и политикой очистки.

Это **не отменяет** необходимость `KnowledgeBaseStoreProtocol`.
Наоборот, внедрение по-прежнему должно начинаться с границы протокола, чтобы новый контур не зацементировал прямую зависимость от одной реализации.

## 4. Целевые сущности

### 4.1 Сущности документа

Серверная часть должна владеть следующими сущностями:

- `upload_id`
- `document_id`
- `document_version_id`
- `document_ref`
- `workspace_id`
- `thread_id`
- `knowledge_collection_id`

### 4.2 Состояние документа

Нужно жёстко разделять:

- состояние документа:
  - файл;
  - извлечённый текст;
  - набор чанков;
  - метаданные;
  - статус эмбеддингов;
  - область в поисковом слое;
- состояние запуска анализа:
  - `question` или `analysis_goal`;
  - `job_id`;
  - статус;
  - артефакт ответа;
  - история конкретного запуска.

Последующий вопрос по документу должен опираться на:

- `document_ref`
- активную область
- новый поиск

А не на один ранее сгенерированный глубокий ответ.

## 5. Целевой поток данных

### 5.1 Поток загрузки

Пользователь загружает файл через `Open WebUI`.

Дальше происходит не внутреннее “магическое знание интерфейса”, а серверный поток обработки:

1. серверная часть принимает метаданные вложения;
2. серверная часть сохраняет файл в общем хранилище;
3. серверная часть создаёт:
   - `upload_id`
   - `document_id`
   - `document_version_id`
   - `document_ref`
4. серверная часть определяет контур подготовки;
5. серверная часть индексирует документ в `Qdrant` в нужную область.

### 5.2 Контуры подготовки

Нужно ввести два рабочих режима подготовки:

#### Быстрый контур

Для обычных документов и слабых машин:

- лёгкое извлечение текста;
- базовое разбиение на чанки;
- эмбеддинги текущим лёгким эмбеддером для поиска;
- быстрое добавление или обновление данных в `Qdrant`;
- документ почти сразу становится доступным для последующих вопросов в чате.

#### Глубокий контур

Для сложных PDF, таблиц, OCR и плохого исходного текста:

- внешняя служба разбора;
- приоритетно `Docling`;
- допустимый резервный вариант — `Tika` или упрощённый извлекатель;
- асинхронная доиндексация;
- обогащение метаданных и, при необходимости, переиндексация версии документа.

### 5.3 Поток чата

Для обычного вопроса по документу:

1. `Open WebUI` передаёт серверной части активные `document_ref`;
2. серверная часть строит поисковый запрос;
3. `Qdrant` возвращает короткий список кандидатов по фильтрам полезной нагрузки;
4. серверная часть применяет правила объединения и повторного ранжирования;
5. ответ формируется с цитированием источников.

### 5.4 Перевод в базу знаний

Нужен отдельный переход:

- область сеанса -> постоянная область базы знаний

Это не должно происходить неявно по самому факту загрузки.
Нужна либо явная команда, либо отдельное серверное правило.

---

## 6. Роль `Open WebUI`

`Open WebUI` в этой схеме:

- основной пользовательский интерфейс;
- место загрузки файлов;
- место обычного чата по документам;
- место выбора явных инструментов;
- место отображения статуса и результатов.

`Open WebUI` в этой схеме **не является**:

- владельцем `document_id`;
- владельцем метаданных корпуса;
- владельцем политики `TTL` и очистки;
- владельцем контура подготовки данных;
- владельцем правил поиска.

То есть `Open WebUI Knowledge` допустимо использовать как пользовательский контур, но только поверх серверной идентичности документа и общего источника поиска, а не как отдельный самостоятельный мир.

---

## 7. Почему единый `Qdrant` здесь полезен

### 7.1 Польза

- Уходит дублирование поисковых контуров между путём сеанса и путём базы знаний.
- Последующий вопрос после загрузки опирается на тот же серверный слой, что и дальнейший поиск по базе знаний.
- Не нужно держать отдельный плотный индекс в памяти только ради `session RAG`.
- Упрощается происхождение источников и их отображение в ответе.
- Легче строить единые фильтры по:
  - `workspace_id`
  - `thread_id`
  - `document_id`
  - `scope`
  - `knowledge_collection_id`

### 7.2 Что важно не сломать

- область `session` не должна смешиваться с постоянным корпусом без фильтров;
- очистка данных сеанса не должна влиять на корпус базы знаний;
- `Open WebUI` не должен напрямую владеть схемой полезной нагрузки;
- код оркестрации не должен протечь деталями `Qdrant` наружу.

---

## 8. Низкоресурсный профиль

Этот документ специально ориентирован на слабые и простые ПК.

### 8.1 Что не берём как базовый вариант

Не считаем базовым решением:

- тяжёлые эмбеддеры уровня `8B`;
- обязательный отдельный reranker;
- визуальный `RAG`;
- эмбеддинги изображений страниц;
- постоянный `OCR` на каждую загрузку;
- многоступенчатый multi-agent конвейер поиска.

Это всё допустимо только как будущий путь для сильного профиля железа.

### 8.2 Что берём как базовый вариант

- один `Qdrant`;
- текущий лёгкий эмбеддер для поиска;
- поиск с приоритетом плотных векторов;
- необязательный локальный `BM25` или объединение короткого списка кандидатов после выборки;
- небольшой `top_k`;
- консервативное бюджетирование контекста;
- асинхронная доиндексация вместо тяжёлого синхронного разбора.

### 8.3 Нормативные правила для слабых машин

- быстрый ответ важнее идеального разбора на первом проходе;
- глубокий разбор должен быть опциональным или фоновым;
- `rerank hook` по умолчанию выключен;
- подготовка данных не должна блокировать интерфейс долгими вычислительными этапами на `CPU`;
- один и тот же документ не должен индексироваться в несколько плотных локальных структур без явной причины.

---

## 9. Требования к полезной нагрузке `Qdrant`

Минимально нужна полезная нагрузка, которая различает жизненный цикл документа:

- `tenant_id`
- `workspace_id`
- `thread_id`
- `knowledge_collection_id`
- `document_id`
- `document_version_id`
- `source_scope`
- `source_origin`
- `mime_type`
- `doc_type`
- `language`
- `created_at`
- `expires_at`
- `ingestion_status`
- `embedding_model_id`

Где:

- `source_scope = knowledge | session`
- `thread_id` обязателен для короткоживущей области сеанса
- `expires_at` обязателен для области сеанса

Дополнительно нужны:

- детерминированные `point_id`
- стабильный `chunk_id`
- контракт на повторную индексацию версии документа

---

## 10. Правила поиска

### 10.1 Общий принцип

Даже если и `knowledge`, и `session` лежат в одном `Qdrant`, правила поиска не должны жить внутри интерфейса.

Серверная часть должна контролировать:

- какие области участвуют в запросе;
- как объединяются `knowledge` и `session`;
- какие фильтры применяются;
- как работают дедупликация и повторное ранжирование;
- как формируется `source_scope_summary`.

### 10.2 Политика по умолчанию

Для обычного последующего вопроса по только что загруженному документу:

- сначала область `session`;
- при необходимости добавляется `knowledge`;
- итоговый короткий список кандидатов собирается в серверном слое правил.

Для обычного чата по базе знаний без активного session-документа:

- используется только область `knowledge`.

### 10.3 Чего делать не надо

Не нужно:

- превращать `knowledge_base_retrieval.py` в тонкий прокси к `Qdrant` без логики;
- уносить правила объединения в трюки промпта;
- считать историю чата единственным контекстом последующего ответа;
- дублировать обычный чат по документу через скрытый вызов инструмента.

## 11. Границы ответственности

### 11.1 У серверной части

- контракт загрузки
- регистрация документа
- `document_ref`
- выбор службы разбора
- разбиение на чанки
- эмбеддинги
- добавление и обновление данных в `Qdrant`
- правила поиска
- явные инструменты
- жизненный цикл заданий
- очистка и `TTL`

### 11.2 У `Open WebUI`

- чатовый интерфейс
- интерфейс вложений
- поверхность `Knowledge`
- выборщик инструментов
- кнопки действий
- отрисовка истории

### 11.3 У внешней службы

- тяжёлый разбор
- OCR
- извлечение таблиц
- глубокая нормализация документа

## 12. Риски и меры снижения

### Риск 1

Данные сеанса останутся в `Qdrant` дольше нужного.

**Мера:**

- обязательный `expires_at`
- задание очистки
- фильтр по `thread_id`
- отделение `session` от `knowledge` на уровне полезной нагрузки

### Риск 2

Пользователь задаст вопрос раньше, чем завершится глубокий разбор.

**Мера:**

- быстрый контур как минимальный индексируемый базовый вариант;
- затем фоновое обогащение;
- версия документа и `ingestion_status` должны быть видимы серверной части.

### Риск 3

`Open WebUI` начнёт выглядеть владельцем документа.

**Мера:**

- жёстко использовать серверные ссылки;
- не передавать инструментам сырые пути файловой системы;
- не считать встроенное состояние интерфейса каноническим состоянием документа.

### Риск 4

Слабые машины не потянут выбранный путь разбора и эмбеддингов.

**Мера:**

- базовый режим только на лёгком профиле;
- тяжёлый разбор только по необходимости;
- без обязательного отдельного `reranker`;
- без обязательной тяжёлой мультимодальной схемы.

---

## 13. Связь с текущими планами

Этот документ:

- сохраняет направление `Open WebUI-first`;
- сохраняет модель владения данными у серверной части;
- сохраняет обязательность `KnowledgeBaseStoreProtocol`;
- сохраняет `Qdrant` как каноническое векторное хранилище;
- уточняет, что путь session-документа тоже должен сходиться к `Qdrant`, но через короткоживущую область, а не через вечный постоянный корпус;
- уточняет базовый низкоресурсный профиль, которого не хватает в более общих migration-планах.

Этот документ не означает:

- немедленный отказ от границы протокола;
- немедленный перенос всей логики в `Open WebUI`;
- обязательный тяжёлый разбор для каждой загрузки;
- обязательный отказ от явных серверных инструментов.

---

## 14. Итоговое решение

Для проекта с ориентацией на слабые ПК и на `Open WebUI-first` целевой архитектурный вариант должен быть таким:

- `Open WebUI` — главная пользовательская оболочка;
- загрузка через `Open WebUI` сразу попадает в серверный поток обработки документа;
- серверная часть создаёт `document_ref` и индексирует документ не во внутреннее “знание UI”, а в управляемый ею контур поиска;
- `Qdrant` становится единым слоем поиска для:
  - постоянного корпуса базы знаний;
  - короткоживущих областей документов сеанса;
- различие между `session` и `knowledge` реализуется жизненным циклом, фильтрами полезной нагрузки и политикой очистки;
- для слабых машин базовый режим строится на лёгком разборе и лёгких эмбеддерах, без обязательного отдельного `reranker` и без тяжёлой мультимодальной схемы.

Если этот документ принимается как проектное решение, следующий шаг — сформировать план внедрения по фазам:

1. граница протокола
2. серверные `upload/document refs`
3. `Qdrant` для областей `session` и `knowledge`
4. лёгкие контуры подготовки
5. интеграция с `Open WebUI` и проверочные сценарии
