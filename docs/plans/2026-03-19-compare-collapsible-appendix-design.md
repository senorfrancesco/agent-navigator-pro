# Compare Collapsible Appendix Design

Дата: 2026-03-19

## Цель

Убрать визуальный шум из основного `Chainlit`-чата при сравнении документов, когда workflow генерирует длинное приложение со списком различий по пунктам.

Пользовательский результат:

- краткий итог сравнения остаётся сразу видимым в основном сообщении;
- длинное приложение со строками различий переносится в отдельный `Chainlit Step`;
- `Step` должен быть схлопнут по умолчанию, чтобы не засорять ленту;
- пользователь при необходимости раскрывает его вручную и видит полный список строк без потери деталей.

## Проблема

Текущий compare-report рендерится как большой markdown-блок. Когда раздел `Приложение: различия по пунктам` содержит десятки или сотни строк, чат становится трудно читать:

- юридический вывод и summary теряются среди массива diff-строк;
- финальный ответ визуально "захламляет" весь thread;
- даже если итог качественный, UX деградирует из-за слишком длинного inline payload.

## Ограничения

- Основной UI проекта — `Chainlit`.
- Решение должно опираться на уже используемый в проекте паттерн `cl.Step`, а не на кастомный frontend.
- Не нужно терять различия: скрытие должно быть purely presentational.
- Существующий report/file/PDF flow не должен ломаться.

## Рекомендуемый UX

### Видимая часть основного ответа

В основном `assistant_message` оставлять только верхнеуровневые секции compare-отчёта:

- `Юридический вывод`
- `Ключевые смысловые различия`
- `Что отсутствует / требует отражения`
- при наличии: короткая summary line о количестве различий

### Скрытая часть

Раздел `Приложение: различия по пунктам` выносить в отдельный `cl.Step`:

- имя `Step`: `Приложение: различия по пунктам (N)`
- `type`: `tool` или другой уже поддерживаемый нейтральный тип
- содержимое: полный markdown приложения без усечения
- `autoCollapse`: `True`, чтобы блок по умолчанию был схлопнут

### Threshold policy

Чтобы не ухудшать UX для коротких сравнений, включать вынос в `Step` только если приложение действительно длинное.

Минимальный рекомендуемый policy contour:

- если различий мало, приложение остаётся inline;
- если различий много или markdown приложения длиннее порога, приложение уходит в `Step`.

Конкретный threshold нужно зафиксировать в коде и тестах, а не подбирать “на глаз” в рантайме.

## Архитектурный подход

Нужно разделить compare-output на две части уже на уровне post-processing в `Chainlit` adapter, а не ломать сам workflow:

1. workflow `compare.py` продолжает генерировать полный `final_report`;
2. `Chainlit`-слой перед отправкой ответа извлекает из markdown:
   - summary/body;
   - appendix section;
3. summary/body отправляется как основной ответ;
4. appendix отдельно отправляется/рендерится через `cl.Step`.

Это предпочтительнее, чем менять сам report contract workflow, потому что:

- сохранится совместимость с текущими tests/report artifacts;
- separation касается presentation layer, а не domain logic compare;
- будет проще переиспользовать тот же полный `final_report` для файлов/PDF.

## Изменяемые зоны

- `backend/orchestrator/chainlit_app.py`
  - compare response rendering
  - helper split markdown -> summary/app appendix
  - `cl.Step` rendering for appendix
- при необходимости:
  - `backend/tests/test_chainlit_streaming.py`
  - `backend/tests/test_compare_workflow.py`
  - новые/расширенные tests на compare presentation behavior

## Риски

### 1. Слишком жёсткий markdown parsing

Если вырезание приложения будет завязано на хрупкий regex, можно случайно повредить основной ответ.

Митигировать:

- парсить только канонический заголовок `## Приложение: различия по пунктам`;
- если секция не найдена, оставлять поведение безопасным fallback: весь report остаётся inline.

### 2. Дублирование контента

Нельзя допустить, чтобы приложение оказалось и в основном сообщении, и в `Step`.

Митигировать:

- helper должен возвращать mutually exclusive parts;
- тестом зафиксировать, что строка заголовка приложения отсутствует в основном сообщении после split.

### 3. Шум от коротких отчётов

Если выносить приложение в `Step` всегда, UX для маленьких compare cases станет хуже.

Митигировать:

- включать collapsible appendix только после порога по числу различий/длине секции.

## Acceptance

- compare-ответ в чате больше не выводит длинное приложение inline по умолчанию, если оно превышает порог;
- верхнеуровневый юридический вывод остаётся сразу читаемым;
- все diff-строки сохраняются в отдельном `Step`;
- `Step` отображается схлопнутым по умолчанию;
- короткие compare-cases не теряют читаемость и не перегружаются лишним `Step`;
- fallback безопасен: если секцию приложения не удалось выделить, compare-ответ остаётся полным и не ломается.
