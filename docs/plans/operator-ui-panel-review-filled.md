## 1. Обзор

Скрин:
- [Обзор](/tmp/operator-ui-overview-2026-04-02.png)

Текущее впечатление:
- Что здесь раздражает или мешает: Страница перегружена текстом — почти каждый блок содержит 2–4 строки описания, которые оператор читал один раз при онбординге, а потом они только занимают место. Карточки путей запуска, блок железа и блок метрик конкурируют за внимание без явной иерархии.
- Что выглядит нормально: Цветовые статус-бейджи (`Готово` / `Нативный запуск`), секция предупреждений справа, общая тёмная тема.

Правки:
- Карточки путей запуска: Убрать описательный текст под заголовком карточки («Локальная среда запуска с оркестрацией через launcher…»). Оставить только: название пути + бейдж статуса + скрипт запуска (одна строка кода). Описание перенести в Help.
- Метрики: Блок «Ключевые сигналы Prometheus» свернуть по умолчанию — показывать только три числа (HTTP-счётчик, оркестрация, деградация) в одну строку без подписей-абзацев. Подписи — в тултип при наведении.
- Железо: Блок «Обнаруженные возможности и базовые env-настройки» заменить компактной строкой: `x86_64 / 63 GB RAM / 2× NVIDIA RTX 2070`. Подробности (инвентарь GPU, glibc, профиль среды) — в Help или в отдельном expandable-блоке «Подробно о железе».
- Предупреждения: Ок. Секция «Блокеры парсинга» уже вынесена отдельно — достаточно бейджа `Требует внимания` в заголовке.
- Здоровье сервисов: Сократить до двух строк: «Нативный запуск: 0/5 готовы, 5 заблокированы» и «Офлайн-бандл: 0/5 готовы». Подробности — на вкладке «Сервисы».
- Последние действия: Перенести в правую колонку и показывать только 3 последних события в виде лога (одна строка на событие), без секции «Зона нет активности».

Тексты:
- Какие формулировки переписать: «Доступность запуска, железо, состояние сервисов и статус парсинга» → «Обзор системы». Длинный подзаголовок убрать совсем — его смысл понятен из структуры страницы.
- Какие термины заменить: «Блокеры парсинга и среды выполнения» → «Блокеры». «Обнаруженные возможности» → «Железо». «Сборные сервисы / Готовность активного пути» → «Сервисы».

Логика:
- Что должно показываться по умолчанию: Статус путей (2 карточки) + компактная строка железа + компактное здоровье сервисов + блокеры (если есть). Всё остальное — свёрнуто или убрано на другие вкладки.
- Какие блоки убрать или свернуть: Блок метрик Prometheus — свернуть. Блок «Последние действия» при нулевой активности — скрыть (показывать только при наличии событий). Описательные абзацы внутри карточек путей — убрать, перенести в Help.

> **Комментарий UX:** Обзор — это дашборд, а не документация. Принцип: оператор за 3 секунды должен понять «всё ок» или «есть проблема». Сейчас этому мешает количество текста. Перенос описаний в глобальную кнопку `?` (Help) решает проблему без потери информации.

## 2. Запуск

Скрин:
- [Запуск](/tmp/operator-ui-launch-2026-04-02.png)

Текущее впечатление:
- Что неудобно: Карточки путей дублируют описание из Обзора. Блок «Следующий шаг» внизу страницы — оператор до него не доскроллит в момент запуска. Профили запуска представлены в виде текстовых карточек, хотя это по сути радио-список.
- Что оставить: Разделение на два пути (Нативный / Офлайн-бандл). Бейджи статуса среды. Блок лога запуска. Чекпоинты пути (строки с готовностью).

Правки:
- Карточка `Нативный запуск`: Убрать абзац описания. Оставить: название + бейдж статуса среды + одна строка команды запуска + три чекпоинта (бейджи в строку). Кнопки «Запустить» и «Показать проверки» — ок.
- Карточка `Офлайн-бандл / Контейнеры`: Аналогично — убрать описание. Три показателя (файл бандла, бинарник Docker, доступ к сокету) отображать в одну строку в виде иконок со статусом, а не текстовых блоков.
- Профили запуска: Заменить карточки на компактный радио-список с одной строкой на профиль: `● Только backend — Готово` / `● ChainIt dev — Готово` / `● Нативный runtime — Готово` / `○ Полный локальный стек — Частично`. Описание профиля — в тултип или Help.
- Лог запуска: Ок. Оставить как есть, но добавить возможность сворачивания.
- Блок `Следующий шаг`: Перенести подсказки оператора («Открой Сервисы», «Открой Конфиг») в топбар после запуска в виде временного баннера или inline-подсказки под кнопкой — не внизу страницы.

Кнопки:
- Что должна делать основная кнопка: Запускать выбранный путь (активный таб). Одна кнопка на карточку, а не глобальная.
- Как должно выглядеть состояние `Запуск / Запуск... / Остановить / Остановка...`: Кнопка меняет текст + добавляет спиннер слева. Цвет: зелёный → серый (при запуске) → красный (Остановить) → серый (при остановке). Состояния не менять на отдельный элемент — достаточно изменения лейбла и цвета.
- Нужны ли дополнительные кнопки: Нет. «Показать проверки» — достаточно.

Логика запуска:
- Что сейчас работает не так: Нет чёткого визуального сигнала «сейчас идёт запуск» на уровне всей страницы — только лог внизу. Оператор может не понять, что процесс уже запущен.
- Что должно происходить после успешного старта: Бейдж в топбаре меняется с «Не запущено» на «Запущено» (зелёный). Карточка пути подсвечивается. В топбаре появляется временная подсказка «Проверь Сервисы».
- Что должно происходить после stop: Бейдж → «Остановлен» (серый). Лог фиксирует событие остановки. Карточка возвращается в исходное состояние.
- Какой статус считать `готово`: Все сервисы выбранного пути отвечают на `/health`. Не «частично», не «наблюдение» — только полный ответ.

## 3. Конфиг

Скрин:
- [Конфиг](/tmp/operator-ui-config-2026-04-02.png)

Текущее впечатление:
- Что неудобно: Секция «Источники конфига» с тремя статус-блоками занимает половину экрана и содержит много текста про «действия оператора». Табы вариантов (8 штук в строку) без группировки — трудно ориентироваться. Пресеты оформлены как карточки с абзацами, хотя это просто две опции.
- Что оставить: Бейджи статуса источников (`Есть` / `Сгенерировано`). Кнопка «Применить изменения». Группировка полей по категориям (режим запуска, GPU, backend).

Правки по структуре:
- Источники конфига: Сжать до одной строки с тремя иконками-статусами: `backend/.env ✓` · `backend/.env.runtime ⟳` · `Цепочка готова ✓`. Описания («канонический env runtime», «сгенерированный применённый план») — в Help. Блок «Действие оператора» убрать — эта информация либо очевидна, либо должна быть в Help.
- Варианты: Сгруппировать 8 табов в 2–3 группы с выпадающим меню или секциями: «Профиль запуска» (Режим запуска, Профиль runtime), «Модели и контекст» (Реестр моделей, LLM/Контекст, Параметры моделей), «Сеть и доступ» (Порты и URL, Секреты и доступ, Профили ChainIt, Парсинг). Активный таб отображать жирным.
- Редактируемые поля: Ок. Три поля с дропдаунами — нормальная плотность. Строки «Применено» и «Источник» — сделать серым мелким текстом под полем, не отдельным блоком.
- Пресеты: Заменить карточки на радио-кнопки с одной строкой: `○ Адаптивный набор` / `○ CPU-режим`. Описание — в тултип `(?)`.
- Валидация: Добавить inline-ошибку под полем при недопустимом значении. Сейчас валидации нет визуально.
- Path picker: Ок.

Главный вопрос по env:
- Должен ли UI считать единственным каноническим источником `backend/.env`: `Да`
- Что делать с `backend/.env.runtime`: Показывать как read-only производный файл. Оператор не редактирует его напрямую — только через Apply. Пометить явно: «Генерируется автоматически — не редактировать».
- Что делать с legacy override-файлами: Показывать предупреждение `⚠ Обнаружен legacy override` с кнопкой «Удалить» или «Показать содержимое». Не молчать.

Runtime preflight:
- Нужна ли отдельная кнопка `Подобрать рекомендуемые параметры`: `Да`
- Где она должна стоять: В секции «Редактируемые поля», рядом с заголовком группы «Режим запуска» — до полей.
- Что именно она должна делать: Запрашивать у backend рекомендованные значения на основе текущего железа и выбранного профиля и подставлять их в поля как «рекомендуемые» (с визуальным выделением — например, синим бордером).
- Что должно применяться автоматически, а что только по подтверждению: Автоматически — ничего. Всё только после нажатия «Применить изменения». Рекомендованные значения — это предзаполнение, не автоприменение.
- Как показывать рекомендованные значения: Поле с рекомендованным значением подсвечивается рамкой + иконка `★` слева. Tooltip: «Рекомендовано на основе железа».

Поля/варианты:
- Какие группы полей лишние: Таб «Парсинг и сравнение» — неочевидное название, непонятно что там без клика. Переименовать или объединить с другим табом.
- Какие группы полей отсутствуют: Нет явной группы для логирования/отладки (уровень лога, verbose-режим).
- Какие поля надо переименовать: `UMS_RUNTIME_PROFILE` → «Профиль runtime». `BACKEND_MODE` → «Режим backend». `DEVICE_MODE` → «Устройство». (Технические имена переменных оставить в мелком тексте под полем как справочное значение, но не как лейбл.)

## 4. Сервисы

Скрин:
- [Сервисы](/tmp/operator-ui-services-2026-04-02.png)

Текущее впечатление:
- Что неудобно: Все 5 карточек сервисов имеют статус «Заблокировано» и показывают одинаковые «не отвечает» + «живой HTTP probe не пройден». Это создаёт информационный шум без actionable вывода. Секция метрик (запросы в работе, UMS, активная модель) — три блока с большим пустым пространством и надписью «к сведению».
- Что оставить: Разделение на «Статус выбранного пути» и «Диагностика парсинга». Ссылки на Grafana/Prometheus. Лог внизу.

Правки:
- Карточки сервисов: Сжать до одной строки на сервис: `● Agent API — http://127.0.0.1:1880/health — Заблокировано`. Убрать повторяющийся текст «не отвечает» и «живой HTTP probe не пройден» — заменить иконкой статуса. При наведении — тултип с деталями. Карточки в сетке 2×N → компактный список.
- Диагностика: Блок «Диагностика по выбранному пути» → показывать только если есть данные. Сейчас показывает «Нет диагностики» пустым блоком — скрыть если пусто.
- Метрики: Три метрики («Запросов в работе», «UMS», «Активная тяжёлая модель») отобразить в одну строку inline без карточек: `Запросов: 0 · UMS: 0 · Модель: нет`. Надпись «к сведению» убрать.
- Ссылки Grafana/Prometheus: Сгруппировать в компактный блок «Наблюдаемость» со списком ссылок — три строки вместо трёх карточек с описаниями.
- Лог-панель: Ок. Добавить кнопку «Очистить» и фильтр по уровню (info / warn / error).

Логика:
- Что считать `не отвечает / заблокировано / снижено / готово`: `Не отвечает` — нет ответа на `/health` за таймаут. `Заблокировано` — сервис не запущен (процесс не существует). `Снижено` — отвечает, но возвращает не 200 или деградирует по метрикам. `Готово` — `/health` возвращает 200 стабильно.
- Нужны ли дополнительные сервисы/пробы: Добавить проверку Docker daemon (для офлайн-пути). Добавить проверку доступности GPU (nvidia-smi).
- Что показывать оператору в первую очередь: Общий статус пути (одна строка), затем список сервисов с проблемами (только не-готовые, если все готовы — показать «Все сервисы работают»).

> **Комментарий UX:** Сейчас страница «Сервисы» читается как список ошибок без контекста. Нужна логика «покажи проблемы первыми» — healthy-сервисы свернуть по умолчанию, проблемные — развернуть автоматически с actionable подсказкой.

## 6. Действия

Скрин:
- [Действия](/tmp/operator-ui-actions-2026-04-02.png)

Текущее впечатление:
- Что неудобно: Страница относительно чистая, но описания под кнопками избыточны — «Перечитать текущее состояние оператора из env-файлов и layout репозитория» можно заменить одной фразой. Блок «Текущие блокеры» показывает пустое сообщение «Backend пока не опубликовал maintenance-блокеры» — лишний шум.
- Что оставить: Структуру «Контролируемые команды оператора» + «Текущие блокеры». Три действия — нормальное количество.

Правки:
- Список maintenance-действий: Убрать описательный абзац под каждым действием. Оставить кнопку + краткий лейбл в одну строку. Описания — в Help или тултип на кнопке.
- Названия действий: «Перезагрузить источники конфига» → «Перечитать конфиг». «Пересчитать пути запуска» → «Пересчитать пути». «Перезагрузить deploy surface» → «Обновить deploy». (Короче, глагол + объект.)
- Блокеры: Скрывать блок «Текущие блокеры» полностью если блокеров нет. Не показывать «Backend пока не опубликовал maintenance-блокеры» — это не информация для оператора.
- Нужно ли больше типизированных сценариев: Да — добавить «Сбросить состояние задачи» (если задача зависла). Возможно «Принудительно завершить процесс» с подтверждением.

Логика:

## 8. Env / Runtime / Preflight

Целевая модель:
- Канонический env-файл: `backend/.env` — единственный файл, который редактирует оператор. Все изменения применяются только через UI (кнопка «Применить изменения»), не вручную.
- Допустимы ли generated env-файлы: Да, `backend/.env.runtime` — генерируется автоматически при Apply и при запуске. Показывать в UI как read-only с меткой «Сгенерировано». Оператор не должен его редактировать.
- Допустимы ли temporary artifacts вне env: Да, но UI должен их явно маркировать как временные и не путать с каноническими источниками.

Runtime preflight:
- Что он должен вычислять: Рекомендуемый профиль runtime (`UMS_RUNTIME_PROFILE`) на основе доступных GPU и RAM. Рекомендуемый режим устройства (`DEVICE_MODE`). Совместимость выбранного профиля с текущим железом.
- Что он должен только рекомендовать: Значения полей — только предлагать, не применять автоматически. Предупреждения о несовместимости (например, GPU-профиль без GPU).
- Что он имеет право менять: Ничего без явного подтверждения оператора.

Operator flow:
- Какой должен быть путь оператора для настройки runtime:
  1. Зайти в Конфиг → нажать «Подобрать рекомендуемые параметры» → preflight заполняет поля рекомендованными значениями.
  2. Оператор проверяет значения, при необходимости меняет вручную.
  3. Нажать «Применить изменения» → `backend/.env.runtime` пересоздаётся, изменения применяются.

## 10. Свободные заметки

- Главный принцип редизайна: **описания → Help, статусы → иконки, карточки → списки**. Это одно решение закрывает 80% проблем перегруженности.
- Help drawer с контекстом по активной странице — это не просто «кнопка справки», это архитектурное решение, которое позволяет сделать основной UI значительно чище без потери информации.
- Цветовая система статусов уже хорошая (зелёный/серый/жёлтый/красный) — не менять. Нужно только унифицировать: сейчас «Готово» иногда зелёный, иногда тёмно-зелёный бейдж разного размера.
- Страница Сборка/Деплой требует отдельного дизайн-сессии — там слишком много логики для одной страницы. Рассмотреть разделение на две подстраницы: «Сборка» и «Деплой».
- Sidebar-блок «Аппаратная среда» — рассмотреть перенос в Обзор в виде компактной строки. Постоянное отображение железа в навигации не несёт ценности после первого знакомства с системой.
