16. UI и orchestration contract для обычного чата поверх инструментов, а не вместо него.
	16.1. Базовый пользовательский сценарий — обычный чат, внутри которого можно явно выбрать действие:
	- сравнение двух документов;
	- анализ одного документа;
	- вопрос по документу / RAG;
	- проверка ТЗ vs КП;
	- общая сводка по документам.
	16.2. Не делать UI в стиле operator control panel с большим числом профилей и малопонятных переключателей. Текущий custom `Chainlit`-контур перегружен и вызывает недоверие у пользователя, если часть переключателей неочевидна или фактически мало влияет на поведение.
	16.3. Целевой принцип:
	- пользователь выбирает действие / инструмент;
	- backend выбирает graph/executor;
	- LLM остаётся общей conversational surface;
	- classifier становится optional helper / planner hint, но не единственным центром маршрутизации.
	16.4. Не отдавать orchestration-логику целиком в UI. Источник истины для routing/tool selection должен оставаться в backend API.
	16.5. Для ближайшего этапа приоритетнее:
	- упростить `Chainlit` до action-first UX;
	- вынести явный `requested_tool` / `requested_graph` contract в backend;
	- оставить `Chainlit` как debug/dev shell, если понадобится;
	- отдельно оценить `Open WebUI` как пользовательский shell поверх уже существующего backend orchestration.
	16.6. `Open WebUI` рассматривать в первую очередь как UI / shell / auth / history layer, а не как место, где живёт основная orchestration-логика системы.
	16.7. Для RAG production-контуров не смешивать:
	- UI-shell;
	- orchestration backend;
	- ingestion / parsing;
	- vector store.
	Они должны эволюционировать независимо.
	16.8. Практический целевой стек на следующих фазах:
	- пользовательский shell: `Open WebUI` или отдельный custom frontend;
	- orchestration: текущий `agent_api` / `orchestration_runtime` / `execution_runtime`;
	- parsing / OCR: внешний document service (`Docling` как предпочтительный кандидат, `Tika` как более простой fallback);
	- vector store: `Qdrant` или другой production-ready retrieval backend;
	- `Chainlit`: dev/debug UI, пошаговая трассировка, smoke-проверки и операторский контур.
	16.9. Важно: задача не в том, чтобы заменить текущую LLM-логику на UI-возможности `Open WebUI`, а в том, чтобы дать поверх существующей системы более понятный чатовый интерфейс с явным выбором инструментов.
